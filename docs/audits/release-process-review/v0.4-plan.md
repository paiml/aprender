# Plan for v0.4 — cut, don't extend

Response to the `agy /grillme` lane (conversation `0fec76b4`), verdict
`do-not-implement-as-written`: *over-engineered for a project shipping via `cargo install`*.

**The plan is a deletion.** v0.1→v0.3 made the document more correct. It did not make it
smaller, and the grill is right that size is now the problem. v0.4 should be roughly a
third of v0.3.

## Where the grill is right

| # | finding | accepted |
|---|---|---|
| 2 | delete §7 — a live-GPU self-hosted runner on a **public** repo is an ACE surface, and `infra#359` already decided this | **yes, in full** |
| 4 | no rollback, no post-publish failure path, no user remediation | **yes — this is the real hole** |
| 3 | nine open decisions is evasion; some close by argument | **partly** — RD-8 yes; others die with the sections they belong to |
| 5 | 13 steps and 700 lines is the wrong ratio | **yes** |

## Where it is wrong, and why

**Finding 1 — "abandon physical dogfooding" goes too far.** The spec exists because of two
defects that recorded evidence structurally cannot catch:

- **#2696** — the published binary silently ignored `--gpu`.
- **#2971** — GPU computed a different function than CPU on a supported model.

`workspace-test`'s sentinels replay recorded evidence against **the tree**. #2696 was a
defect in **the tarball a user installs**. No amount of in-tree testing sees it: that is
the whole content of #2869, and it is why §1.2 says *"a binary is verified when it is
installed from the release asset"*. Deleting the physical dogfood deletes the only check
aimed at the class that actually shipped.

What is over-built is the **machinery**, not the purpose: 8 cells, 4 artifacts × 2 models
× 2 backends × 2 hosts, a slot manager, a promotion job, cross-machine receipt passing.

**The 80/20 the grill asked for:** one host, one model, two backends, after the tag.
`lambda-labs` already has the 7B and a 4090. Install the released asset, run it CPU and
GPU, record one receipt. That catches both #2696 and #2971 and costs one manual run.

not) · §5.2's manifest work · §10's refusals · the four-artifact matrix.

# Revision after the `/teamwork` review

Lane `d9a2d701` returned `do-not-implement-as-written` on the plan above. **Four of its
five findings are accepted, and the first one breaks the plan's central argument.**

## The argument above is wrong

The plan said in-tree testing "structurally cannot see" a tarball defect, therefore
physical dogfooding. The lane's counter:

> a CI workflow can download the built release asset, install it, and execute it (e.g.
> testing `--gpu`), fully verifying the installed artifact without manual physical
> dogfooding.

That is correct, and the plan conflated two different claims:

- **"test the artifact, not the tree"** — sound, and non-negotiable. #2696 was a defect
  in the tarball.
- **"therefore test it by hand on owned hardware"** — does *not* follow. CI can install
  from the release and run it.

**What CI cannot do is run it on a GPU it does not have.** That is the whole residue, and
it is much smaller than §5:

| defect class | needs a GPU? | where it runs |
|---|---|---|
| `--gpu` refused on a driverless host (FX-17), install works, binary runs, registry prints | **no** | hosted CI, on the downloaded asset |
| `--gpu` silently falls back on a host *with* a GPU (#2696) | **yes** | a GPU host |
| GPU computes a different function than CPU (#2971) | **yes** | a GPU host |

And a live-GPU lane already exists: `cuda-nightly` on `gx10`, which is what
`infra#359` Option A left in place. The plan deleted §7 and did not say where live-GPU
release checks go. Accepting Option A implies the answer, but implying is not stating.

## Revised change set

| § | action |
|---|---|
| **§5 (new shape)** | **automate, do not delete.** A CI job installs from the release asset and runs the artifact checks that need no GPU. The GPU cells run on the **existing `cuda-nightly` gx10 lane** against the same asset. Nothing is done by hand |
| §5.3 | cells cut for *scope*, not for automation: one model (7B), CPU and GPU. **`gx10` is kept** — dropping the only aarch64 host while shipping an aarch64 artifact is a regression, and RD-6 stays open rather than being closed by omission |
| §7 | still deleted as written — no PR-time live-GPU check on a laptop-class runner on a public repo — but §5 now **names `cuda-nightly` on `gx10`** as where live-GPU release verification happens |
| §2 | host slots still go: with the work automated onto an existing lane there is no fleet to schedule |
| §8 | `check_release_receipts.sh` **survives**. If receipts exist, a guard reads them; the lane is right that deleting the enforcement while keeping the artifact is the pendulum swinging |
| **§13 Rollback** | must carry a **fire drill**: an automated yank path, exercised on a dummy release on a schedule. That is rollback's equivalent of a registered failing mutation — a rollback nobody has executed is a rollback that does not work |
| §11 | RD-8 closed by argument. RD-6 **stays open** |

## Net effect versus the first plan

Same reduction in machinery, arrived at by **automation rather than amputation**. The
release still verifies the artifact a user installs — which is the point — but no step is
manual, `gx10` keeps aarch64 covered, and the guard that reads the receipts stays.

## What the lane did not answer

Q6 — anything both the grill and the plan miss — came back uncovered. Still open.

## The open question neither plan answers

Is **one** post-tag dogfood cell enough, or does dropping `gx10` give up the aarch64
coverage that RD-6 was about? Cutting to one host closes RD-6 by making it moot — which
is a decision, and therefore not mine.
