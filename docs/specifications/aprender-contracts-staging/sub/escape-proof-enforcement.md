# Escape-Proof Contract Enforcement

Version: 1.0
Status: proposed
Date: 2026-04-09

> Sub-spec of [pv-spec.md](../pv-spec.md) | Section 13

## Principle

**It must be impossible to ship code that violates a contract.**

Not "difficult." Not "caught in CI." Impossible. The compiler refuses to
produce a binary. Like a type error — you can't cast a String to an int,
and you can't ship a function without its proven contract.

> **Implementation Status (2026-04-03):** The full escape-proof pipeline is
> partially implemented. Stages A, C, D, E, F are implemented. Stage B (Lean
> verification in build.rs) tracks status but does NOT enforce at compile time.
> The `#[contract]` macro uses `option_env!()` (not `env!()`), so missing
> contracts produce no assertions rather than compile errors. The escape analysis
> table below marks planned-but-unimplemented items with ⚠️.

## The Six-Stage Pipeline

Each stage gates the next. Skip one → compile error (see status notes).

```
A. Equation (YAML)
   ↓ must exist
B. Lean 4 Proof (lakefile.lean)
   ↓ must have no sorry
C. YAML Contract (contracts/*.yaml)
   ↓ pv lint Gate 1-4 must pass
D. build.rs Codegen
   ↓ generates debug_assert!() from preconditions/postconditions
E. #[contract] Macro
   ↓ checks CONTRACT_* env var from build.rs, inserts assertions
F. Test Execution
   ↓ cargo test runs falsification tests, failures block
```

### Stage A: Equation

The YAML `equations:` section declares the mathematical ground truth.

```yaml
equations:
  softmax:
    formula: "σ(x)_i = exp(x_i) / Σ_j exp(x_j)"
    preconditions:
      - "!logits.is_empty()"
      - "logits.iter().all(|x| x.is_finite())"
    postconditions:
      - "ret.len() == logits.len()"
      - "ret.iter().all(|&v| v >= 0.0 && v <= 1.0)"
      - "(ret.iter().sum::<f32>() - 1.0).abs() < 1e-6"
    lean_theorem: "ProvableContracts.Theorems.Softmax.PartitionOfUnity"
```

### Stage B: Lean 4 Proof

The `lean_theorem:` field references a proven theorem.

> **Current status:** Lean proof status is TRACKED (via `pv lean-status`)
> but NOT ENFORCED at compile time. build.rs does not verify theorem
> existence or sorry status. This is a planned upgrade — the `LeanStatus`
> enum (Proved/Sorry/Wip/NotApplicable) exists in lean_gen/mod.rs.

**Planned enforcement** (not yet implemented) — build.rs would verify:

```rust
// build.rs
fn verify_lean_theorems(contracts: &[Contract]) {
    for (name, eq) in &contract.equations {
        if let Some(theorem) = &eq.lean_theorem {
            // Check lean/ directory for the theorem
            let lean_src = find_lean_source(theorem);
            if lean_src.is_none() {
                compile_error!("Lean theorem {theorem} not found");
            }
            if contains_sorry(&lean_src) {
                compile_error!("Lean theorem {theorem} contains sorry");
            }
        }
    }
}
```

This mirrors SPARK/Ada's approach: GNATprove must discharge ALL proof
obligations before SPARK code compiles. We use Lean 4 + lake as our prover.

### Stage C: YAML Contract Validation

`pv lint` runs 4 gates:
- Gate 1 (validate): YAML parses, schema valid
- Gate 2 (audit): internal consistency (obligations ↔ harnesses)
- Gate 3 (score): completeness metrics
- Gate 4 (verify): ALL test: references resolve to fn test_* in src/

Any gate failure = `pv lint` exits non-zero = CI blocks.

### Stage D: build.rs Codegen

build.rs reads YAML `preconditions:` and `postconditions:`, generates
Rust assertion code:

```rust
// Auto-generated by build.rs from contracts/softmax-kernel-v1.yaml
// DO NOT EDIT — regenerate with `pv codegen`

/// Preconditions for equation `softmax`
#[inline(always)]
pub fn check_softmax_pre(logits: &[f32]) {
    debug_assert!(!logits.is_empty());
    debug_assert!(logits.iter().all(|x| x.is_finite()));
}

/// Postconditions for equation `softmax`
#[inline(always)]
pub fn check_softmax_post(ret: &[f32], logits: &[f32]) {
    debug_assert!(ret.len() == logits.len());
    debug_assert!(ret.iter().all(|&v| v >= 0.0 && v <= 1.0));
    debug_assert!((ret.iter().sum::<f32>() - 1.0).abs() < 1e-6);
}
```

Generated code uses `debug_assert!()` — **zero cost in release builds**.
Generated file is `include!()`'d — missing file = compile error.

### Stage E: #[contract] Macro

The proc macro on the implementing function:

```rust
#[contract("softmax-kernel-v1", equation = "softmax")]
pub fn softmax_1d(logits: &[f32]) -> Vec<f32> {
    // build.rs sets CONTRACT_SOFTMAX_KERNEL_V1_SOFTMAX=bound
    // If missing: compile_error!("contract binding not found")
    // Macro also inserts: check_softmax_pre(logits) at entry
    // and check_softmax_post(&ret, logits) before return
}
```

The macro does THREE things:
1. Verifies CONTRACT_* env var exists (compile-time binding check)
2. Inserts precondition assertions at function entry
3. Inserts postcondition assertions before return

### Stage F: Test Execution

Falsification tests run the function against known inputs and verify
outputs match the equation. `cargo test` failure = CI blocks merge.

The tests are referenced in the YAML `falsification_tests:` section
and verified to exist by `pv lint` Gate 4.

| Remove #[contract] | pv lint Gate 4: test refs don't match → CI blocks | ✅ Implemented |

| Remove preconditions | pv lint Gate 5: warning for missing pre/post | ✅ Implemented (warning, not error) |
| Weaken postcondition | Lean proof status tracking | ⚠️ Planned: build.rs compile_error! |

## Design Principles (from research)

### From Eiffel: Syntactic Impossibility of Contract Removal

Eiffel's Assertion Redeclaration Rule makes it **grammatically impossible**
to weaken a postcondition in a subclass:

- `require else new_pre` — OR'd with parent (can only weaken precondition)
- `ensure then new_post` — AND'd with parent (can only strengthen postcondition)

Writing bare `ensure` in an override → **compiler rejects it**. You cannot
remove a postcondition — the syntax does not permit it. We implement
the same principle: `#[contract]` macro checks binding exists at compile
time. No binding → compile_error!. Not "CI catches it" — the compiler
itself refuses.

### From SPARK/Ada: Graduated Verification with Non-Zero Exit

SPARK's five assurance levels (Stone → Platinum). `gnatprove` generates
verification conditions and dispatches to Z3. Key mechanism: **non-zero
exit code if ANY VC is unproved and unjustified**. CI runs:
```
gnatprove --mode=gold
```
Unproved check = build fails. Escape hatches (`pragma Assume`,
`pragma Annotate`) are **separately countable and auditable** — they're
not hidden, they're tracked. 95-98% of checks prove automatically.

Our equivalent: `pv lint` returns non-zero if Gate 4 or Gate 5 fails.
Lean sorry = unproved VC = build.rs compile_error!.

### From Lean 4: Three-Layer Sorry Detection

1. **Compiler warning** (`warn.sorry`, default true)
2. **Axiom audit** (`#print axioms` shows `sorryAx` transitively)
3. **lean4checker** (independent kernel replay of .olean files)

Mathlib4 runs lean4checker in CI. Any PR with sorry → rejected.
Our build.rs uses layer 2 (axiom grep for sorryAx in .olean output).

### From Dafny: Auto-Active + Auditable Escape Hatches

Dafny generates VCs from specs, Z3 discharges them. If Z3 can't prove →
compile error. Escape hatches exist (`assume`, `{:verify false}`) but
`dafny audit` **enumerates all assumptions**. No hidden escape.

Our `pv lint` Gate 5 is the equivalent audit — it lists every equation
without preconditions. Nothing is hidden.

## Zero Runtime Cost Guarantee

- `debug_assert!()` expands to NOTHING in `--release` builds
- Lean proofs are checked at build time, not runtime
- `#[contract]` macro generates compile-time checks only
- No assertion strings in release binary
- No performance overhead, no binary size increase

The release binary is identical to one built without contracts.
The proof exists in the build artifacts, not the shipped code.

## Lean-Kani Verification Composition

Lean and Kani are NOT interchangeable — they prove different things
about the same obligation. Full design in
**[lean-kani-composition.md](lean-kani-composition.md)**.

| | Lean 4 (L5) | Kani (L4) |
|---|---|---|
| **Proves** | Algorithm correctness over ℝ | Rust code correctness over f32 |
| **Catches** | Wrong formula, missing invariant | Overflow, NaN, precision loss, code paths |
| **Bridge** | — | `stub_float`: assumes Lean's postconditions on transcendentals |

The `stub_float` strategy is the key composition point: Kani replaces
`f32::exp()` with `kani::any()` constrained to Lean's proven properties
(positive, finite), then verifies the surrounding Rust code preserves
the structural invariant regardless of exp's exact value. Lean discharges
the hard math, Kani verifies the structural code.
