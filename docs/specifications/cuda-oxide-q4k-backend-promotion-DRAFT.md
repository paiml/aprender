# cuda-oxide Q4K Dequant-Matvec Backend Promotion — Design & Feasibility (DRAFT)

Status: DRAFT / scope-only — NOT implemented, no PR.
Author: autonomous scoping pass, 2026-06-15.
Ticket (proposed): PMAT-OXIDE-Q4K-001.

## 1. Problem & Goal

The pure-Rust **cuda-oxide** Q4K dequant-matvec kernel is reportedly:
- **1.45× faster** than the existing hand-PTX `TiledQ4KGemv` on Blackwell (sm_121), and
- **immune to the GH-480 sm_121 JIT miscompile** (unconditional-backward-branch loop-drop bug)
  that the current PTX path must work around at load time via
  `patch_backward_branches_sm121` (`crates/aprender-gpu/src/driver/ptx_patch.rs`).

Goal: ship that kernel as a real, selectable CUDA backend in aprender **without** making the
normal `aprender-serve` build depend on the cuda-oxide toolchain.

### The hard constraint

cuda-oxide requires **nightly-2026-04-03 + LLVM-21 + cargo-oxide (ALPHA, gx10-only)** to BUILD.
Standard aprender CI/build (stable-ish, self-hosted runners, no LLVM-21) cannot compile it.
Therefore **aprender-serve must NOT have a build-time dependency on cuda-oxide / cargo-oxide.**

## 2. Feasibility verdict: GO via pre-generated embedded PTX

**Confirmed on gx10 (`gx10-a5b5`, GB10 Blackwell sm_121).** `cargo oxide pipeline` /
`cargo oxide build` emit a **standalone `.ptx` text file**:

```
✓ PTX written to .../async_vecadd/async_vecadd.ptx (target: sm_121)
[device_codegen] Embeddable artifact generated: async_vecadd.ptx (Ptx, target: sm_121)
```

The emitted file is plain PTX assembly with the exact shape our loader already consumes:

```ptx
//
// Generated by LLVM NVPTX Back-End
//
.version 8.8
.target sm_121
.address_size 64

.visible .entry vecadd(
    .param .u64 .ptr .align 1 vecadd_param_0,   // &[f32] data ptr
    .param .u64               vecadd_param_1,   // &[f32] len (slice fat-ptr)
    .param .u64 .ptr .align 1 vecadd_param_2,
    .param .u64               vecadd_param_3,
    .param .u64 .ptr .align 1 vecadd_param_4,
    .param .u64               vecadd_param_5
) { ... }
```

This is **identical in kind** to the runtime-generated PTX that
`CudaModule::from_ptx(ctx, &ptx)` already loads. So the integration path is:

> **Generate the Q4K kernel PTX once on gx10, commit the `.ptx` as a static asset,
> `include_str!` it into `aprender-serve`, load it at runtime via the existing
> `CudaModule::from_ptx` → `cuModuleGetFunction` → `cuLaunchKernel` path, behind a
> non-default runtime/feature toggle. NO cuda-oxide build dependency.**

`--arch <ARCH>` (e.g. `--arch sm_121`, `sm_90`, `sm_120`) is a real `cargo oxide` flag, so we
can regenerate per-arch variants from the same Rust source if/when we want sm_89 (RTX 4090)
coverage. The committed v1 asset is sm_121-only (the only arch where this kernel currently wins
+ is needed to dodge GH-480).

### Why this is clean

The aprender CUDA stack already loads opaque PTX strings and is fully cubin-cache-aware:
- `CudaModule::from_ptx` (`crates/aprender-gpu/src/driver/module.rs`) takes a `&str` of PTX,
  JIT/links to cubin, and caches the cubin to `~/.cache/trueno/ptx/{sha256}.cubin`. Embedding a
  pre-generated PTX string is a first-class supported input, not a hack.
- The existing hand-PTX launch in `q4k_gemv_cached_uses.rs` is exactly the call shape we reuse.

## 3. ABI mapping (the one real wiring subtlety)

Current hand-PTX `TiledQ4KGemv` uses a **C-style 5-arg ABI** (see
`crates/aprender-serve/src/cuda/executor/q4k_gemv_cached_uses.rs`, all four launch sites):

```
(out_ptr: *f32, weight_ptr: *u8/Q4K, in_ptr: *f32, k: u32, n: u32)
```
launched as 5 entries in `&mut [*mut c_void]`, plus a launch config of
`grid=(num_blocks,1,1)`, `block=(128,1,1)` for the tiled variant, where one block produces
`outputs_per_block=4` rows.

cuda-oxide emits the **Rust slice fat-pointer ABI**: every `&[T]` / `&mut [T]` parameter becomes
**two PTX params** `(ptr: .u64 .ptr, len: .u64)`. Scalars stay as one param each. So a Rust
kernel signed as:

```rust
#[kernel]
fn q4k_gemv(out: &mut [f32], weight: &[u8], x: &[f32], k: u32, n: u32) { ... }
```

emits PTX params:
```
out_ptr, out_len, weight_ptr, weight_len, x_ptr, x_len, k, n   // 8 params
```

**Two mapping options — pick at kernel-authoring time on gx10, BEFORE generating the asset:**

- **Option A (recommended): author the cuda-oxide kernel with a raw-pointer + explicit-len ABI**
  so the emitted PTX matches the existing C-style 5-arg shape (out, weight, x, k, n). cuda-oxide
  supports raw device-pointer args (see `cuda_module_contract` example: "raw device pointer
  argument"). This makes the aprender-side launch site **byte-for-byte the existing arg array** —
  minimal new Rust, maximal reuse of `q4k_gemv_cached_async`.
- **Option B: keep the natural slice ABI** and write a new launch wrapper in aprender-serve that
  pushes 8 `*mut c_void` entries (ptr,len pairs + scalars). More faithful to idiomatic
  cuda-oxide but requires a bespoke launch site and careful len/dim bookkeeping.

Recommendation: **Option A.** Define the kernel ABI to mirror the existing kernel so the only
delta on the aprender side is *which PTX string and entry-name we load*, not how we marshal args.
The launch config (grid/block/outputs_per_block) is reused verbatim; the kernel must be authored
to the same tiling contract (128 threads/block, 4 outputs/block, K%256==0, atomic/shared
reduction per row).

The entry-point name in the PTX (`.visible .entry <name>`) becomes the `kernel_name` string
passed to `stream.launch_kernel(...)`. Pin it to a stable name, e.g. `oxide_q4k_gemv`.

## 4. Recommended integration path (exact files)

### 4.1 Static asset
- New file: `crates/aprender-serve/src/cuda/ptx/oxide_q4k_gemv.sm_121.ptx`
  (the committed, pre-generated PTX). Plus a sidecar `oxide_q4k_gemv.sm_121.ptx.meta.json`
  recording: cuda-oxide commit/version, nightly date, LLVM version, arch, source-kernel sha256,
  generation date, and the `.entry` name. This is the provenance/sync anchor.
- Verify it is **not gitignored** (CB-510 lesson): `git check-ignore -v <path>` must return
  non-match; the `ptx/` dir must be tracked. Add to `Cargo.toml` `include = [...]` so it ships in
  the crates.io package (it is referenced by `include_str!`, so it must be packaged).

### 4.2 Loader + dispatch (feature- and runtime-gated)
- `crates/aprender-serve/src/cuda/executor/q4k_gemv_cached_uses.rs`:
  in `q4k_gemv_cached_async` (and the indexed/`q4k_gemv_cached` siblings), add a branch:
  - **when** `cfg!(feature = "cuda-oxide-ptx")` AND runtime profile selects oxide AND device is
    sm_121 AND K%256==0 → use cache_key `"oxide_q4k_gemv_{k}_{n}"`, and on cache-miss compile via
    `self.compile_ptx(include_str!(".../oxide_q4k_gemv.sm_121.ptx"))` instead of
    `self.kernels.generate_ptx(...)`. Launch with the existing 5-entry arg array (Option A) and
    the existing `LaunchConfig` for tiled.
  - **else** fall back to the current `KernelType::MwvQ4KGemv` / `TiledQ4KGemv` path (unchanged).
- New feature flag in `crates/aprender-serve/Cargo.toml`:
  `cuda-oxide-ptx = ["cuda"]` (pure additive; embeds the asset, no new deps). Keep it
  **off by default**; opt-in only. Add the corresponding `apr serve`/profile flag (e.g.
  `--q4k-backend oxide|tiled|auto`) wired through `gpu_profile` so it is selectable at runtime
  without recompiling.
- `crates/aprender-serve/src/cuda/gpu_profile.rs`: add a `q4k` backend enum field (mirror the
  existing `Q6kVariant`/`mwv_warps` precedent) so dispatch reads one profile field.

### 4.3 No changes to the build pipeline
- `crates/aprender-serve/build.rs` is **untouched** for codegen — PTX is a committed asset, not a
  build product. (Optionally add a `cargo:rerun-if-changed` on the `.ptx` for hygiene.)
- `aprender-gpu` (`trueno-gpu`) loader is reused as-is. `CudaModule::from_ptx` already handles
  sm_121 (PTX 8.8 native target) and the cubin disk cache.

## 5. Parity / regression gate plan

Template: `crates/aprender-serve/tests/q4k_gemv_parity.rs` (already exercises GPU-vs-CPU Q4K with
both synthetic and real GGUF weights, tolerance `rel_err < 1%` real / `1e-3` synthetic).

New gate: `crates/aprender-serve/tests/q4k_gemv_oxide_parity.rs`
(`#![cfg(all(feature = "cuda-oxide-ptx", feature = "cuda"))]`):

1. **Bit/eps parity vs CPU reference** — reuse `create_test_q4k_weights` + real-model weights;
   assert oxide-PTX output matches `fused_q4k_parallel_matvec` within the existing Q4K eps band
   (`sqrt(K)*2^-23*|dot|`, per `q4k-cross-backend-parity-v1.yaml` `dot_product_epsilon`).
2. **Three-way parity** — oxide-PTX vs existing TiledQ4KGemv hand-PTX vs CPU on the SAME weights
   & input; assert oxide ≈ tiled ≈ cpu. This is the load-bearing regression (catches PTX drift).
3. **Entry-name + module-load smoke** — assert `CudaModule::from_ptx(include_str!(asset))` loads
   and `get_function("oxide_q4k_gemv")` resolves. Fails loudly if a regenerated asset renamed the
   entry or broke the header.
4. **State-isolation** (per aprender-serve CLAUDE.md) — run the kernel twice, assert identical
   output (no accumulator/buffer-reuse leak).
5. **End-to-end coherence (F-LAYOUT-001 style)** — `apr run <q4k.gguf> --gpu --q4k-backend oxide
   --prompt "2+2="` must produce coherent output (not garbage), proving row-major ABI is correct.

Contract: extend/clone `q4k-cross-backend-parity-v1.yaml` → `q4k-oxide-backend-parity-v1.yaml`
(add a `backend_match` equation: `|dot_oxide - dot_tiled| < sqrt(K)*2^-23*|dot_tiled|`). Validate
with `pv validate` (NOT bash), per the contract-first mandate. Coverage must co-evolve
(Rule 7) — the new launch branch needs the new test + contract uplift in the same PR.

**Beat-as-CI artifact** (10-day campaign lane): add a BeatBenchmark gate asserting the oxide
backend's measured tok/s on sm_121 ≥ 1.25× the tiled path on the same model, so the perf win is
falsifiable in CI on gx10 (gate runs only where `cuda-oxide-ptx` + sm_121 present).

## 6. Risks & mitigations

| Risk | Severity | Mitigation |
|------|----------|------------|
| **PTX is `.target sm_121`-locked** (header pins sm_121; won't load on sm_89 RTX 4090). | High for portability | Gate the oxide path on `device.compute_capability().0 >= 12` (Blackwell+). Fall back to tiled/mwv on sm_89. v1 ships sm_121-only by design (only arch where it wins + dodges GH-480). For sm_89 coverage later, regen with `cargo oxide build --arch sm_89` and commit a second asset. |
| **Maintenance / drift** — PTX is a committed binary-ish artifact; the Rust kernel source lives in the cuda-oxide toolchain on gx10, not in CI's build graph. Kernel change ⇒ stale PTX. | Medium | (a) Commit the **kernel Rust source** alongside the asset under `crates/aprender-serve/src/cuda/ptx/src/` (NOT compiled by aprender; doc/provenance only). (b) Sidecar `.meta.json` with source sha256. (c) Three-way parity test (§5.2) fails if PTX semantics drift from tiled/CPU. (d) Document the regen recipe (below) and add a `make regen-oxide-ptx` target that ssh's gx10. |
| **PTX portability across CUDA driver/toolkit versions** — JIT/link behavior can change; cubin cache keyed on driver version already (`module.rs` cache key = sha256(ptx+target+driver_version)). | Low–Medium | Cache key already invalidates per driver version, so a driver bump just recompiles the committed PTX (PTX→cubin is forward-stable for a fixed `.version 8.8`). Parity test runs per-CI so a JIT regression is caught. |
| **Slice-ABI mismatch** (8-param fat-pointer vs 5-param C-style) silently mis-marshals args ⇒ garbage/crash. | High if wrong | Author kernel with raw-ptr ABI (Option A) so the arg array is unchanged; lock the contract with the entry-name smoke test (§5.3) + e2e coherence test (§5.5). A param-count mismatch surfaces as a launch failure or garbage, both caught. |
| **GH-480 assumption** — claim is cuda-oxide avoids the backward-branch JIT bug. | Low | The loader's `patch_backward_branches_sm121` runs on ALL PTX with major>=12, so even if the oxide PTX *did* contain the pattern it would still be patched. The win is that oxide PTX shouldn't need it; verify via parity test passing without relying on the patch (log if patch_count>0 on the oxide asset). |
| **crates.io packaging** — `include_str!` asset not in published tarball. | Medium | Add `ptx/` to `Cargo.toml` `include`; run `bash scripts/check_package_includes.sh` post-add. CB-510 root-anchored gitignore check. |
| **Process-level PTX blocklist** (`BROKEN_PTX`) poisons the oxide kernel if it ever fails once. | Low | Expected behavior; the parity gate ensures the asset compiles before merge, so blocklisting only triggers on genuine env breakage. |

## 7. Regeneration recipe (documented, run on gx10 only)

```bash
# On gx10 (has nightly-2026-04-03 + LLVM-21 + cargo-oxide):
cd <cuda-oxide-kernel-project>           # the Q4K kernel crate (to be committed as source)
cargo oxide build q4k_gemv --arch sm_121 # emits q4k_gemv.ptx
sha256sum src/q4k_gemv.rs                 # record in .meta.json
# copy q4k_gemv.ptx -> aprender repo:
#   crates/aprender-serve/src/cuda/ptx/oxide_q4k_gemv.sm_121.ptx
# update oxide_q4k_gemv.sm_121.ptx.meta.json (version/commit/llvm/nightly/arch/sha256/entry-name)
# run parity gate on gx10:
cargo test -p realizar --features cuda-oxide-ptx --test q4k_gemv_oxide_parity -- --test-threads=1
```
