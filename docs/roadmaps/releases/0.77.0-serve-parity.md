## 2. Exit (done_when)

**Measurement:**
- **Host and model:** lambda-labs RTX 4090; Qwen3.5-4B Q4_K_M; one GGUF file, read by its sha256, for all three engines and for S6 on the Orin.
- **Versions:** llama.cpp and ollama pinned, each version recorded in the receipt.
- **Runs:** n=5 per cell; ratios as medians. Where a threshold is stated, LCB95 is the lower bound of a one-sided 95% t-interval (4 degrees of freedom) on the 5 per-run ratios, each run of apr paired with an interleaved run of the reference engine.
- **Receipts:** under `evidence/serve-parity-077/<date>/`, one JSON per cell.
- **Exit codes:** 0 PASS (GREEN), 1 FAIL, 2 NOT_MEASURED, 3 YELLOW. A crash or OOM is FAIL; NOT_MEASURED counts red.
- **Binary:** the apr build is pinned with `scripts/apr_bin.sh`, and its version+SHA are in every receipt.
- **Batch settings:** `CUDA_MAX_BATCH` and `CUDA_BATCH_WINDOW_MS` are set explicitly for every serve run and recorded in the receipt, with the :392 start line as proof of what was used.

**Exit cells:**
- **S1 correctness (expected green):** GREEN when all three hold:
  - `apr serve` and `apr run` emit identical token ids for 20 fixed prompts under greedy decoding (SP-02).
  - #2815, #4979, #3111, #4378 and #4374 are closed, each with a falsifier.
  - A GPU request that cannot fit is refused by name, with no silent CPU fallback (#4969, #5325's exit).
  - Otherwise RED.
- **S2a c=1 decode vs llama.cpp (expected red):** GREEN when apr ÷ llama.cpp tok/s (tg128) has LCB95 ≥ 0.90; otherwise RED. The receipt reports the ratio against SP-00 either way.
- **S2b ollama floor (expected green or red; unmeasured on Qwen3.5 until SP-00):** GREEN when apr ÷ ollama tok/s (tg128) has LCB95 ≥ 0.90; otherwise RED. This is stricter than the `beat-ollama` contract, which applies 0.90 to a median of 7.
- **S3 prefill (expected red):** GREEN when apr ÷ llama.cpp pp512 has LCB95 ≥ 0.80, #4376's own target; otherwise RED.
- **S4 serving shape (expected green or yellow):**
  - c=1 is the baseline. At each c ∈ {4, 8, 16}, at least one `[PMAT-044] Batch m=N` line with N > 1 appears in the receipt (an env var is not proof).
  - Every request's tokens equal its c=1 tokens.
  - c=16 wall time ≤ 2/3 of 16 serial requests (the C-06 falsifier).
  - A turn-2 chat request on the same session hits the prefix cache: TTFT ≤ 50% of turn 1's, with the hit logged (C-08, #4274).
  - GREEN: all four hold. YELLOW: batches form, output is token-equal and the turn-2 hit is logged, but the 2/3 or 50% bound misses. RED: no batch forms, output differs, or the turn-2 request misses the cache or its hit is not logged. Batches that form at some but not all of c ∈ {4, 8, 16} are YELLOW, with the missing c named.
- **S5 API (expected green):** GREEN when both hold:
  - C-04: a live `/api/chat` response has the same key set as the pinned ollama's response to the same request, checked by a key diff.
  - C-13: `/v1/embeddings` is live, with cosine ≥ 0.99 against llama.cpp's embedding of the same text and GGUF, both mean-pooled over the last hidden state and L2-normalised; the receipt records the pooling mode of each engine.
- **S6 edge (expected yellow):**
  - Receipt: model size, GGUF sha256, and peak memory measured by `tegrastats` over the run.
  - GREEN: Qwen3.5 serves within 8 GB unified memory (tegrastats peak) on the Orin (#5321), and, on the same Orin and GGUF (#5276), apr decode tok/s at or above the `beat_threshold` floor in `contracts/beat-ollama-decode-throughput-speed-v1.yaml` relative to ollama's, and apr TTFT within the same floor of ollama's (TTFT is lower-is-better).
  - YELLOW: it serves within 8 GB, but either ratio is below 0.90.
  - RED: it does not serve within 8 GB.
- **Reported, not scored:** the Q2 cell (Qwen3.5-9B) S2/S3 ratios; the C-07 paged-KV trace (SP-12).
