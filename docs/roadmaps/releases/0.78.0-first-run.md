## 2. Exit bar

**The unit is the first-run script** in §6: the commands a new user would type, run from nothing against the binary under test, on each certified host.

The epic is done when all of these hold:

1. Every command in the script exits 0.
2. The script contains no cache path and no hash.
3. The `apr` lines of the script are extracted from the README quick start by a command, so there is no second copy. The isolation, the readiness wait and the checks belong to the harness and do not appear in the README.
4. `apr` reaches its first complete reply in no more commands than Ollama and llama.cpp do. The count is commands typed after install. The competitor versions are the ones pinned in the harness and are written into the receipt.
5. Every row in §3 is green.

The release does not wait for the bar. On 12-11 each row is scored GREEN or RED from a run on the pinned release binary; a red row is named in the release notes and carries to 0.79.

**Known red at baseline:** every row in §3 fails on `apr 0.75.4`. A row whose `done_when` already passes when its work starts is dropped, not ticked.

**Negative control:** the script run against `apr 0.75.4` must be RED. A harness that passes 0.75.4 is broken.

**Positive controls:** one per competitor, each from nothing for that tool, with the same prompt as the script. Ollama: a separate `ollama serve` started by the harness on its own `OLLAMA_HOST` with `OLLAMA_MODELS` set to an empty directory (the `ollama run` client alone ignores that variable). llama.cpp: `LLAMA_CACHE` set to an empty directory. Each must return a reply longer than 32 tokens that ends at end of turn. The model, quantization and tool versions are pinned in the harness. A competitor that fails its own control is RED as a harness and cannot be the bar.

Every receipt carries the `apr` version and sha, each competitor's version, the host, and the model repo and revision. Receipts go under `evidence/first-run-078/<date>/`.

**GATE or LAB:** the first-run contract is LAB. It can block no merge and no release. Making it a GATE needs the operator's yes, three green nights on main and one gate retired; this plan does not ask for that.

## 6. Commands

Baselines: §6 of `crux-ux-first-run-analysis-2026-11-27.md` holds one block per measured finding, F-01 to F-11 (F-12 is read from the README).

The first-run script, as it would read once the rows are green. The binary under test is already on `PATH`; installing it is not part of the script.

```bash
#!/usr/bin/env bash
set -euo pipefail
D=$(mktemp -d); export HOME=$D XDG_CACHE_HOME=$D/.cache
S=
trap '[ -z "$S" ] || kill "$S" 2>/dev/null || true; rm -rf "${D:?}"' EXIT
cd "$D"
M=Qwen/Qwen2.5-Coder-0.5B-Instruct

# README line 1
apr run hf://$M "Explain quicksort in three sentences." --temperature 0 > reply.txt
[ "$(wc -w < reply.txt)" -gt 32 ]   # more than 32 words is more than 32 tokens
! grep -q '=== ' reply.txt
# README line 2
apr list > list.txt; grep -Fq "$M" list.txt

# README line 3
apr serve run $M --port 18080 & S=$!
ok=0; for i in $(seq 1 60); do curl -sf -o /dev/null localhost:18080/health && { ok=1; break; }; sleep 1; done; [ "$ok" = 1 ]
# README line 4
curl -sf localhost:18080/v1/chat/completions -H content-type:application/json \
  -d '{"model":"'$M'","messages":[{"role":"user","content":"What is 2+2?"}]}' > chat.json
jq -e '.choices[0].message.content | test("4")' chat.json > /dev/null
kill "$S"; wait "$S" || true; S=

# README line 5
apr rm $M
apr list > list.txt; ! grep -Fq "$M" list.txt
```

The script needs `bash`, `curl` and `jq`.

Ollama = `ollama run <name> "<prompt>"` (1) and llama.cpp = `llama-cli -hf <org/repo> -p "<prompt>"` (1) are from the vendors' documentation today (cited; the analysis matrix shows 2 for each because it counts the install); the positive controls of §2 replace them with measured counts when U-00 lands.
