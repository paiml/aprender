# 0.71 V3: the serving-shape parity receipt (spec section, draft)

Exit criterion V3 (APR-LOOKAHEAD-001 §2a) reads "batched decode with a serving-shape parity receipt".
No document on main defines that receipt. This section defines it. It is staged on a branch during S-1,
and it moves into the 0.71 serve spec when one exists.
Executable reference: `scripts/lookahead/v3_shape_check.py`. Draft contract: `contracts-draft/serving-shape-parity-v1.yaml`.
Case table: `scripts/lookahead/fixtures/v3/cases.json`, 21 rows, each a fixture with its exit code and its exact reasons.
As staged, the script's `--self-test` runs only the six original fixtures and compares exit codes. `0.71-v3-selftest-cases.patch`
makes it run the whole table.

## What exists on main (measured 2026-10-03)
- **Correctness witness.** `scripts/perf041_batched_parity_probe.py` (PP-26 v3.1, FALSIFY-CB-006/008) runs in cuda-nightly
  and is checked at release by `check_perf041_marker.sh`. It gates (a) intra-batch agreement (every slot agrees with
  slot 0 to `declared_min`) and (b) no frozen slot. Agreement with the m=1 reference (`divergence_at`) is
  **recorded, not gated**, because the m=1 and batched engines select different kernels, and without a top-2 margin
  a temperature-0 near-tie cannot be told apart from a wrong-KV divergence.
- **Speed bands.** `evidence/parity-http/bands/{apr,llamacpp}-c{1,4,8,16}.json` (2026-08-25). At c=4 on that run,
  apr produced 112 tok/s with TTFT p50 3453 ms, and llama.cpp produced 481 tok/s with TTFT p50 15 ms. The model identity is not recorded,
  so this is history only and not a baseline.

## The latest lambda witness is not admissible as a V3 receipt
`python3 scripts/lookahead/v3_shape_check.py evidence/perf041/lambda/witness.json` returns NOT ADMISSIBLE, with these reasons:
1. The model is qwen2.5-coder-1.5b, not the blessed Qwen3.5-4B.
2. c=16 formed m=14, so the shape that was served is not the shape that was claimed.
3. At c=4, 8 and 16 the batch diverges from m=1 at token 3 (declared_min 64), and no near-tie margin was recorded.
perf041 itself reports PASS on every band, and that is correct for the question perf041 answers.

## Definition
A V3 receipt is a perf041 witness (same schema, same probe) that also holds all of the following:
| # | Rule | Why |
|---|---|---|
| S1 | model = blessed Qwen3.5-4B, sha256 recorded | V1–V3 are claims about that model |
| S2 | bands c ∈ {1, 4, 8, 16} all measured | the serving shapes `apr serve` advertises |
| S3 | `m_formed == c` for every band | a band that formed m < c served a different shape; it is reported under m, never claimed as c |
| S4 | identity: `binary_sha256`, `commit`, `host`, `prompt_sha256` (and the APR-OBS-001 §2.1 block once OBS-00 lands) | no ratio or claim across mismatched identity |
| S5 | `divergence_at ≥ declared_min` vs m=1, **or** the witness records `top2_margin_at_divergence < ε` (ε = 0.05 logit, `[A]`) | this turns the recorded-only m=1 comparison into a gate. It needs the server to expose the top-2 logits at the divergence position (the "master S12 row 22" gap cited in the probe) |
| S6 | perf041 result PASS per band (intra-batch agreement, no frozen slot) | unchanged |
| S7 | FALSIFY-CB-004: per-request decode at c=4 ≥ 50% of c=1, from the same run | batching must not trade correctness for collapse |

`v3_shape_check.py` checks S1–S6. It does not check S7, because the perf041 witness records no timing. S7 is the parent
contract's FALSIFY-CB-004, measured on the same run, and the receipt cites that measurement beside the witness.
Speed against llama.cpp at the same c is **reported beside** the receipt (aggregate tok/s, TTFT p50) and is not part of V3.
The TTFT bound is V1 (`apr-serve-ttft-v1`).

## Work implied (proposed tickets; the cop mints)
- **V3-a:** the server exposes the top-2 logit margin per step behind a debug header, and perf041 records `top2_margin_at_divergence`.
  Without this, S5 cannot pass for any batched band unless the kernels agree to 64 tokens.
- **V3-b:** add Qwen3.5-4B to the perf041 nightly model set on lambda and gx10.
- **V3-c:** find the cause of the c=16 m=14 slot formation (admission or KV budget?), using five whys before any fix.
- **V3-d:** port the check to Rust. Its case table is `scripts/lookahead/fixtures/v3/cases.json`, and its first defects are
  findings F1–F6 in the draft contract (for example, an unreadable witness exits 1 instead of RED). Then wire it into the
  release gate beside `check_perf041_marker.sh`, behind the contract. The Python script stays a hand-run external check and
  is never invoked by the build.

## Open questions (not rulings)
- Is ε = 0.05 logit right? It should be calibrated from the margin distribution of measured near-ties once V3-a lands.
- Should S5 also bound how many near-tie divergences a run may have (e.g. at most 1 per band)? Otherwise a systematic kernel error
  could hide behind many small margins.
