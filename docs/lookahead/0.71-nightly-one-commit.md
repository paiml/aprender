# 0.71 look-ahead: start every nightly verdict producer on one commit (scope only)

Status: scope. No ticket, PR or workflow edit. It is useful only if the
release train adopts the "shared commit" rule, where the judge reads the
commit the producers ran on, not main's head at the 04:45Z read.

## How this was measured (0 GitHub calls)

- **Producer runs:** the `runs.tsv` of the 2026-10-04 and 2026-10-05
  bundles of `scripts/release/nightly_train.sh`. The 04:45Z timer saved
  them. They hold every scheduled run on main of each producer in the lane
  table back to 09-21, with run head and start time.
- **Main's head at a time:** `git log --first-parent origin/main`.
  Committer time is a few seconds to minutes earlier than the push, so a
  merge landing right at 04:45Z can be off by one.
- **Night N:** runs started from N 20:00Z to N+1 20:00Z. Only runs that
  started before the N+1 04:45Z read are counted.

Findings:

1. **The two verdict producers on main today never split.** They ran on
   one commit on all 7 nights, because they fire within about 30 min of
   each other.
2. **The head rule voided 2 of 7 nights** (10-02, 10-04). In both, merges
   landed after the producers started and before the 04:45Z read. The
   shared rule would have judged those 2 nights.
3. **With the wider producer set, splits are common.** The set that the
   verdict lanes are being wired to adds deep-nightly (cron 20:30Z),
   release-gates-nightly (22:15Z), release-lanes-nightly (23:17Z) and
   models-nightly (22:17Z/23:17Z), so it spans 20:30Z..23:17Z crons. Over
   all scheduled producers that fired before 04:45Z, the night ran on 2 or
   more commits in **3 of 7** nights (09-28, 10-02, 10-04). Neither rule
   can judge a split night: it is not_measured under both.
4. **These four producers are not measured here.** They are not in the
   judge's lane table yet, so the saved read holds none of their runs. The
   3 of 7 figure is a proxy taken from the producers that are in the read.
   It becomes exact with one per-workflow runs read each (4 REST calls with
   ETag), or once the lanes are wired and the judge's read carries them.

Schedule events on this account fire 3h51m..6h49m late (see the comment
in `release-gates-nightly.yml`). So separate crons do not order the
producers, and any merge during that spread splits the night.

## Sketch: one run, one commit

**Recommended: A, one caller workflow.** Add `nightly-verdict.yml` with a
single cron. Its first job resolves nothing: the run's own `github.sha`
is C. It then calls each verdict producer as a reusable workflow:

- Add `on: workflow_call` next to each producer's existing `schedule`.
- Each producer checks out `${{ github.sha }}` (nightly.yml checks out
  its gate job's output sha, so that job reads `github.sha` too).
- Remove each producer's own cron after one green overlap night.

What this gives:
- Every lane runs on exactly C, so a merge cannot split the night.
- The schedule delay is paid once, not six times.
- The judge reads one run.

What the judge needs:
- In the lane table, each verdict lane's producer becomes
  `.github/workflows/nightly-verdict.yml`, with a job-name pattern of
  `<caller job> / <callee job>`.
- One read covers every lane, which saves calls under GH-1.
- Keep the self-test row that names a killed lane. A failed callee is a red
  job in the same run.

Costs and risks:
- All six producers have a workflow-level `concurrency:` group. How a
  callee's group behaves when it is called from one run is unverified, and
  must be checked on a dispatch drill before relying on it.
- The runner fan-out lands at one moment, so the label pools must hold all
  verdict jobs at once (or use `needs:` to stagger them).
- None of the six producers calls another workflow today, so nesting
  depth is not a concern.

Rejected:
- **B, tag + dispatch.** The caller pushes `refs/tags/nightly/<D>` at C
  and dispatches each producer `--ref nightly/<D>`. The runs are
  `workflow_dispatch`, which the judge counts as drills and never as a
  night. It needs a judge rule change and a ref write per night.
- **C, pin file.** The first producer records C and later ones check it
  out. Their `github.sha` still differs, so the judge's "run head = C"
  match breaks. The judge would have to trust an artifact's claim of C,
  which is weaker evidence.

Order, if the shared rule is chosen:
1. Wire the four lanes into the judge's table.
2. Then A, as one PR per producer that adds `workflow_call` (no behaviour
   change), then one PR that adds the caller and repoints the lanes.
3. Gate-graph check before any lane moves.
