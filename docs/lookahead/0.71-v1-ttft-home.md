# V1/V2 TTFT: the gate already has a home (L1 correction, 2026-10-03)

Look-ahead L1, train 0.71, epic #3598. Branch-only under C277. Nothing here
runs, mints or opens anything. Every file cited is on `origin/main` @ `316dee2cd4`,
except where a line says otherwise.

## What L1 got wrong

`la-71/serve-ttft-v1` drafted a receipt schema of its own, `apr-serve-ttft-v1`,
and a checker of its own, `scripts/lookahead/ttft_receipt_check.py`. The checker
has:

- its own estimator: the median of the raw samples, with at least 5 samples;
- its own bound, hardcoded as `BOUND = 2.0`;
- its own pin, hardcoded as `PIN = "d1d3c3396"`.

Before drafting, L1 checked origin for an existing producer, but only against
`scripts/lib/bench_receipt.py`. That missed the spec that already owns this
metric. So the draft was a **second definition** of how the project measures
TTFT, in two ways:

- Its estimator disagrees with the spec's.
- Its threshold sits outside `scripts/perf-matrix.yaml`. PP-33 forbids exactly
  that: `parity_block.py` lost its `FLOOR`/`CEILING` constants for the same reason.

## What V1 needs: PROPOSE only, these are spec-owner rulings

**R-71-6: where the gate lives.** L1 recommends making V1 the first latency
bound in P-8: ttft at c=1, W1.

- The value goes in `perf-matrix.yaml` (PP-33), not in a script.
- The estimator stays as it is, called with the lanes swapped:
  `paired_ratio_lcb(comparator, subject, ttft_p50_ms, 0.95)`. Swapping keeps
  "higher is better", so the 5th-percentile convention needs no change.
- V1 holds iff LCB95(comparator/subject) >= 0.5. That is the same as saying apr's
  TTFT is at most 2x llama.cpp's, at 95%.
- The alternative is the standalone `apr-serve-ttft-v1`. Choosing it means
  keeping a second estimator, and P-8 would still say "no latency bound".

**R-71-7: which model.** V1 names Qwen3.5-4B, but the §8 REFERENCE cell is
Qwen2.5-Coder-7B Q4_K_M. There are three options:

- Add a Qwen3.5-4B cell beside the reference cell. The `d1d3c3396` pin exists
  for Qwen3.5 support (changelog 3.1, "the 0.68 Qwen3.5 scope (#3329) had no
  comparator at the old pin"). That pin's only Qwen3.5 evidence is a CPU build
  on `intel` that loads Qwen3.5-0.8B and emits one token. At `316dee2cd4`, no
  Qwen3.5 cell exists in §8, §12 or perf-matrix.yaml, so this option costs a
  new cell, and a 4B GGUF gets its first GPU comparator run.
- Switch the reference cell itself to Qwen3.5-4B. This restarts row 18, and
  no ratio already measured on the 7B carries over to the new model.
- Measure V1 on the reference cell. Then row 18 produces V1 with no extra run,
  but V1's text changes to the §8 model.

The baseline-plan note that called the pin-bump evidence "wrong model" was
measured against V1's text, not against §8.

**Wiring: one ticket per item, all after LIVE. PROPOSE-TICKET, not minted.**

- (a) Rust `perf_gate` receipt: emit the ttft ratio and its bound beside `dec`.
  The Rust producer governs.
- (b) `perf_receipt.py` `_ratios_for`: add `ttft` beside `dec`. This is the
  legacy path.
- (c) `perf_gate.sh`: gate ttft at c=1 against the matrix value.
- (d) `perf-matrix.yaml`: move `ttft` from `reported` to `gated.c1`, with its bound.

## V2 (`load_ms`)

PP-LLAMA-001 §3 has no load metric.

- aprender-cd's harness (`la-71/bench-ready-ms@ae507a2acf`) stamps
  `runs[*].cold_start_ms` and `cold_start_resolution_ms`, but only under `--start`.
- The canonical producer runs `--url` against servers it started itself.
  `check_no_competing_harnesses.sh` forbids it from timing them, so it cannot
  measure load_ms.

Proposal: add a §3 row `load_ms`, defined as the time from spawn to the first
passing readiness probe. It is an upper bound, reported with its resolution,
measured by the client, and REPORTED with no bound. Each lane gets one `--start`
replicate that feeds a `load` block in the receipt. This proposal is folded into R-71-6.

`crux-C-27-v1` already has a startup bound:
`time_to_first_ready(apr run 7B.gguf) < 1000 ms`, where ready means the
tokenizer is loaded and the graph is built. It differs from `load_ms` in three
ways:

- it times `apr run`, not `apr serve`;
- its ready is a state inside the process, not a probe the client sees;
- it is bounded, where `load_ms` would be REPORTED.

C-27 is a draft ("DO NOT promote to ACTIVE until: (1) evidence collected").
The spec owner decides whether §3 names one quantity or two.

## What happens to `la-71/serve-ttft-v1`

It is **withdrawn as the V1/V2 contract**. It is not deleted.

Its case table moves into `perf_gate.sh`'s mutation suite when (c) lands
(fold = move). These cases are new to that suite:

- a fabricated p50;
- failed requests;
- a summary-only lane;
- a coarse load bracket;
- too few samples.

The provenance, pin and join cases are already covered by `bench_receipt.py`
and `perf_gate.sh`. The real `llamacpp-d1d3c3396.json` stays as the real-data
RED case: it has failed requests, and its `prompt_tokens` is 144, not 512.
