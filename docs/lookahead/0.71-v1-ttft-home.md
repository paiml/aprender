# V1/V2 TTFT: the gate already has a home (L1 correction, 2026-10-03)

Look-ahead L1, train 0.71, epic #3598. Branch-only. Nothing here
runs, mints or opens anything. Every file cited is on `origin/main` @ `316dee2cd4`,

## What L1 got wrong

`la-71/serve-ttft-v1` drafted a receipt schema of its own, `apr-serve-ttft-v1`,
and a checker of its own, `scripts/lookahead/ttft_receipt_check.py`. The checker
has:

- its own estimator: the median of the raw samples, with at least 5 samples;
- its own bound, hardcoded as `BOUND = 2.0`;
- its own pin, hardcoded as `PIN = "d1d3c3396"`.

Before drafting, L1 checked origin for an existing producer, but only against
`scripts/lib/bench_receipt.py`. That missed the spec that already owns this
metric. So the draft was a **second definition** of how the project measures
TTFT, in two ways:

- Its estimator disagrees with the spec's.
- Its threshold sits outside `scripts/perf-matrix.yaml`. PP-33 forbids exactly
  that: `parity_block.py` lost its `FLOOR`/`CEILING` constants for the same reason.

## What V1 needs: PROPOSE only, these are spec-owner rulings

**R-71-6: where the gate lives.** L1 recommends making V1 the first latency
bound in P-8: ttft at c=1, W1.

- The value goes in `perf-matrix.yaml` (PP-33), not in a script.
- The estimator stays as it is, called with the lanes swapped:
  `paired_ratio_lcb(comparator, subject, ttft_p50_ms, 0.95)`. Swapping keeps
  "higher is better", so the 5th-percentile convention needs no change.
- V1 holds iff LCB95(comparator/subject) >= 1 - δ, with δ = 0.5 in the matrix.
  That is V1's target, apr TTFT <= 2x llama.cpp's, at 95% confidence.
- The alternative is the standalone `apr-serve-ttft-v1`. Choosing it means
  keeping a second estimator, and P-8 would still say "no latency bound".

## V2 (`load_ms`)

PP-LLAMA-001 §3 on main has no load metric.

- aprender-cd's harness (`la-71/bench-ready-ms@7b16abdc02`) stamps
  `runs[*].cold_start_ms` and `cold_start_resolution_ms`, but only under `--start`.
- The canonical producer runs `--url` against servers it started itself.
  `check_no_competing_harnesses.sh` forbids it from timing them, so it cannot
  measure load_ms.

The v3.2 draft adds the §3 row `load_ms` (`la-71/pp-llama-p8-ttft@0494f5b9ff`;
the branch head is `e2d9d734b0`). It is measured by the client, REPORTED with no
bound, and folded into R-71-6:

- It is taken per lane, once per receipt, after `warmup_loads_per_lane` discarded
  loads, from spawn to the first passing readiness probe. The client probes
  `GET /health`, then `/v1/models`, then `/`. The first path that gives a verdict
  decides: 2xx is ready, 5xx is not, and a 4xx or no answer gives none. The probe
  that passed is recorded as `probe`, and the last one that did not as `refusal`.
- It is an upper bound. Its resolution is the measured bracket, from the last
  failing probe sent to the first passing probe answered (`Readiness::resolution_ms`,
  `crates/aprender-test-lib/src/llm/benchmark.rs:283-299` at
  `la-71/bench-ready-ms@7b16abdc02`). The poll interval is carried separately and
  is only the bracket's floor once a probe has failed. `e1f32ac9e5` gave the poll
  interval as the resolution; `0494f5b9ff` corrects it.
- Both lanes load under one declared page-cache mode, `warm` (the whole model
  resident) or `evicted` (none of it), witnessed just before each load. A side is
  UNMEASURED, with its reason, when its witness is absent or disagrees with the
  mode, when its eviction failed, when its report has no cold start or lacks the
  bracket or the 2xx probe, or when the subject took another compute class.

Appendix B carries it as `load{…, subject, comparator}`. Every side carries
`status`, `status_reasons`, `bench_rc`, `evict_rc`, `page_cache` and its start
log. Only a MEASURED side carries `load_ms`, `resolution_ms`, `probe`, `refusal`,
`first_request_ttft_ms` and `first_request_reason`. These keys were checked
against aprender-cd's producer, `la-71/load-block@eca952b489`, which is on
origin, and Appendix B was corrected to match in `d67b6539da`. Each lane's load
pass runs before its bands: one discarded warm-up load, then one measured
`--start` load (`scripts/parity_host_receipt.sh`, `run_load`).

`crux-C-27-v1` already has a startup bound:
`time_to_first_ready(apr run 7B.gguf) < 1000 ms`, where ready means the
tokenizer is loaded and the graph is built. It differs from `load_ms` in three
ways:

- it times `apr run`, not `apr serve`;
- its ready is a state inside the process, not a probe the client sees;
- it is bounded, where `load_ms` would be REPORTED.

C-27 is a draft ("DO NOT promote to ACTIVE until: (1) evidence collected").
The spec owner decides whether §3 names one quantity or two.

## Which KV cache a V1 run times (2026-10-05)

Is `crates/aprender-serve/src/gpu/scheduler/forward_block.rs:387`, which builds a `StreamingKVCache` on every
`generate_refcell` call, on the Qwen3.5-4B serve path? **No**, for `apr serve` and `apr run --gpu` alike, on `main` @
`d66b225880`. So there is no constructor time to put before and after the `StreamingKVCache` lazy-allocation work.
That work (`build-kaizen/flake0-kvcache-lazy-alloc`, not on `main`) changes host caches only.

- **That line belongs to `GpuModel`.** The server reaches `GpuModel` only through `AppState::with_gpu_model` and
  `with_gpu_model_and_vocab`, and every caller of those is a test.
- **Routing.** `apr serve` sends a `qwen35` GGUF to `start_qwen35_server` before any other GGUF path
  (`crates/apr-cli/src/commands/serve/handler_gpu_completion.rs:395-397`). `hybrid_forward_handles` is
  `architecture == "qwen35"` (`crates/aprender-serve/src/gguf/transformer.rs:124-126`). One `Qwen35Session` serves
  every request, one at a time.
- **The cache is `Qwen35CudaState`** (`crates/aprender-serve/src/gguf/cuda/forward_qwen35_cuda.rs:102`), built by
  `build_state` (`:683`):
  - It is device memory, one per session, and later requests reuse it.
  - Each attention layer gets a K and a V buffer of `num_kv_heads × attn_head_dim × capacity` f32. Each buffer is
    allocated and zeroed on the device (`:377-383`), and the stream is synchronised before first use.
  - Every layer also gets a conv state and an SSM state, uploaded as zeros. Their size does not depend on capacity.
- **Allocation.** Nothing is allocated before the first turn: the state is `None` and the capacity 0
  (`crates/aprender-serve/src/gguf/inference/forward/qwen35_session.rs:59-62`, `:428-431`).
  - The first turn sizes it with `grown_capacity` (`:909-926`): at least `MIN_CAPACITY` = 4096 positions (`:33`),
    doubled until prompt plus budget fits, and capped at the context length.
  - A later turn that does not fit gets a new, larger state, and the history is prefilled again (`ensure_capacity`).
- **Size.** For the 4B file (8 attention layers of 32, 4 KV heads, `attn_head_dim` 256 from the header's `key_length`,
  not checked against the tensor), the KV is 64 KiB per position, so 256 MiB at the first capacity of 4096.

What this means for the V1 cell (§12 row 24 of the PP-LLAMA-001 draft):

- **Warm up first.** The first request a server process answers pays for allocating and zeroing the state inside its
  TTFT. A W1 run discards at least one warm-up request per server process, or the c=1 `ttft_ratio` times an
  allocation rather than a prefill.
- **Keep requests within capacity.** A request whose prompt plus `max_tokens` exceeds the current capacity pays for a
  new state and a second prefill. W1 requests stay within 4096 positions, or the run reports which samples grew it.
- **Check the GPU engaged.** If the device does not engage, `apr serve` warns "the default GPU could not be used,
  serving on the CPU", unless the GPU was asked for explicitly, which `refuse_unengaged_accelerator` turns into an
  error (`crates/apr-cli/src/commands/serve/server.rs:178-185`). A V1 run asks for the GPU explicitly and cites the
  backend line from its log.
