## What a binding is here

Each of the 48 contracts gets

```yaml
entity:
  type: code
  ref: <crate>::<module>::<fn>
```

`ref` is the symbol of one of the contract's own rows in a
`contracts/*/binding.yaml`. That row's symbol has `sym:resolved true` in
`origin/main:contracts/contracts.nt`, and it is a free function (`sym:kind fn`).
Nothing was written by hand. `code` is a Σ type marked `implemented: true`.

## Why not 100

Main has exactly 100 unbound contracts with at least one resolved binding row.
52 of them are left out, because binding them would anchor a contract to a
thing the graph cannot tell apart:

| Excluded | n | Defect | Unblocks by |
|----------|--:|--------|-------------|
| Method rows only | 27 | A row naming `module` + `method` resolves to the FIRST `impl` with that method name. Three of the five rows checked by hand resolved to the wrong type (cross-entropy to `MSELoss`, batchnorm to `LayerNorm`, rmsnorm to `GroupNorm`). | Qualify each row with its type, as #4709's branch does for five rows. YAML only. |
| File name shared with another contract | 24 | The graph names a contract `contract/<stem>`, so `contracts/apr-cli-v1.yaml` and `contracts/aprender/apr-cli-v1.yaml` are ONE node. A binding row names a stem, not a path. | Rename the duplicate, or key the contract IRI by path (a pv change). |
| Not walked by census | 1 | `contracts/entrenar/kaizen/` is below the depth census walks. | Move the file up a level, or walk deeper. |

With all three fixed, the same rule gives 148, exactly the step. 27 more
contracts have binding rows that do not resolve at all; those are the margin.
