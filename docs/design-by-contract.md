# Design by Contract in provable-contracts

provable-contracts is the contract library for the Sovereign AI Stack. It
converts peer-reviewed research papers into mathematically provable kernel
implementations through a YAML contract intermediary. Every equation published
in a paper gets a machine-readable contract, and every contract generates
Rust test scaffolds, property-based tests, Kani bounded model checking
harnesses, and Lean 4 theorem prover stubs.

## Pipeline Overview

The codegen pipeline has seven phases:

1. **Extract** -- Read a research paper, identify equations and invariants.
2. **Contract** -- Encode each equation in a YAML contract file.
3. **Scaffold** (`scaffold`) -- Generate Rust trait stubs and failing tests.
4. **Property Test** (`probar_gen`) -- Generate probar/proptest harnesses from proof obligations.
5. **Implement** -- Write the kernel (scalar, AVX2, PTX) in the target crate.
6. **Verify** (`kani_gen`) -- Generate `#[kani::proof]` harnesses for bounded model checking.
7. **Prove** (`lean_gen`) -- Generate Lean 4 theorem and definition stubs.

Phases 3, 4, 6, and 7 are fully automated by this library.

## Contract YAML Schema

Each contract is a self-contained YAML file with the following top-level sections:

| Section | Required | Purpose |
|---------|----------|---------|
| `metadata` | yes | Version, author, description, paper references, dependency list |
| `equations` | yes | Named equations with formula, domain, codomain, invariants |
| `proof_obligations` | no | Typed obligations (invariant, bound, equivalence, ...) with tolerances |
| `kernel_structure` | no | Phase decomposition of the kernel (find_max, exp_subtract, ...) |
| `simd_dispatch` | no | Maps equation names to scalar/avx2/neon dispatch targets |
| `enforcement` | no | Named rules with severity and test references |
| `falsification_tests` | no | Popperian falsification tests -- each predicts behavior and diagnoses failure |
| `kani_harnesses` | no | Bounded model checking harness definitions (strategy, solver, bound) |
| `verification_summary` | no | Aggregate Lean 4 proof status across obligations |
| `qa_gate` | no | Certeza QA gate integration (checks, pass criteria) |

### Proof Obligation Taxonomy

The `obligation_type` field classifies each obligation using one of twelve types:
`invariant`, `equivalence`, `bound`, `monotonicity`, `idempotency`, `linearity`,
`symmetry`, `associativity`, `conservation`, `ordering`, `completeness`, `soundness`.

### Lean 4 Integration

Each proof obligation may carry a `lean` block specifying the theorem name,
Lean module, proof status (`proved`, `sorry`, `wip`, `not-applicable`),
dependencies, and Mathlib imports. The `lean_gen` module uses these to emit
`.lean` files with theorem stubs.

## Binding Registry

A binding registry is a separate YAML file (one per target crate) that maps
contract equations to actual Rust functions. The `contracts/aprender/binding.yaml`
file, for example, contains 284 bindings covering softmax, RoPE, attention,
activation, normalization, and optimizer kernels.

Each `KernelBinding` entry records:
- `contract` -- the YAML contract filename
- `equation` -- the named equation within that contract
- `module_path` / `function` / `signature` -- the implementing Rust function
- `status` -- `implemented`, `partial`, or `not_implemented`

The binding registry enables two key workflows:
- **Audit** (`pv audit --binding`): reports which obligations have implementations and which are gaps.
- **Wired tests** (`pv probar --binding`): generates property tests that call real functions instead of `unimplemented!()`.

## Drift Detection

The `diff` module compares two versions of a contract and produces a
`ContractDiff` with per-section added/removed/changed items and a suggested
semver bump (patch, minor, major). Removing an equation or obligation triggers
a major bump; adding new tests triggers a minor bump; cosmetic metadata changes
trigger a patch bump.

## Coverage Reports

The `coverage` module computes cross-contract obligation coverage. For each
contract it counts:
- Equations, proof obligations, falsification tests, Kani harnesses
- Binding status (implemented, partial, missing)
- Per-obligation-type breakdown

The `overall_percentage` function reports what fraction of obligations are
backed by at least one test or harness.

## Kani Bounded Model Checking

Each contract may declare `kani_harnesses` with a strategy
(`exhaustive`, `stub_float`, `compositional`, `bounded_int`), a solver,
and a bound. The `kani_gen` module emits `#[kani::proof]` Rust functions
that exercise the kernel against the contract's proof obligations.

## Integration with the Sovereign AI Stack

provable-contracts integrates with four sibling crates, each at Level 3
(compile-time enforcement via `build.rs` + `#[contract]` proc macro):

| Crate | Role | Binding file | Policy | Coverage |
|-------|------|--------------|--------|----------|
| **aprender** | ML training library | `contracts/aprender/binding.yaml` | AllImplemented | 284 bindings |
| **realizar** | Model inference engine | `contracts/realizar/binding.yaml` | WarnOnGaps | 23/23 (100%) |
| **entrenar** | Training & optimization | `contracts/entrenar/binding.yaml` | WarnOnGaps | 81/96 (84%) |
| **trueno** | SIMD-accelerated compute | `contracts/trueno/binding.yaml` | AllImplemented | 22/22 (100%) |

Each downstream crate's `build.rs` reads its binding registry from
`../provable-contracts/contracts/<crate>/binding.yaml` and emits
`CONTRACT_*` env vars (e.g. `CONTRACT_SOFTMAX_KERNEL_V1_SOFTMAX=implemented`).
These are consumed at compile time by the `#[contract]` proc macro.

The 107+ contract YAML files cover activations (SiLU, GELU, SwiGLU), attention
(MHA, GQA, flash attention), normalization (RMSNorm, LayerNorm, BatchNorm),
positional encoding (RoPE, ALiBi, absolute position), loss functions
(cross-entropy), optimizers (AdamW, L-BFGS, CMA-ES), classical ML (k-means,
PageRank, decision trees, ARIMA), training infrastructure (learning rate
schedules, gradient clipping, distributed training, VRAM management), and
architecture-level constraints.

## CLI

The `pv` CLI (provable-contracts-cli) exposes every pipeline phase:

```
pv validate contracts/softmax-kernel-v1.yaml   # Parse + validate
pv scaffold contracts/softmax-kernel-v1.yaml    # Generate Rust stubs
pv probar   contracts/softmax-kernel-v1.yaml    # Generate property tests
pv kani     contracts/softmax-kernel-v1.yaml    # Generate Kani harnesses
pv audit    contracts/softmax-kernel-v1.yaml    # Traceability audit
pv coverage contracts/                          # Cross-contract coverage
pv diff     old.yaml new.yaml                   # Drift detection
pv lean     contracts/softmax-kernel-v1.yaml    # Lean 4 stubs
```
