## NP regressors: scope and the gappy rule

Flagged before the options: refusing regressors on the neuralprophet arm *entirely* is not
available, because SC5 requires "a test at `n_lags = 0` proving the imputed-day value is unread",
which only exists if regressors reach the NP arm lag-free.

### Q1 — What fires when `n_lags > 0`?

| Option | Description | Selected |
|--------|-------------|----------|
| Refuse only when gaps exist | `n_lags > 0` AND missing days in `[first, last]`. Gap-free + lagged keeps working; message names the gap. Spike 014's ranked #1 | ✓ |
| Refuse whenever `n_lags > 0` | Simpler predicate, no gap detection. Refuses a well-defined case to avoid a cheap check | |
| Require grid-complete values on NP | `len == (last - first + 1) + horizon` on the NP arm. Honest, but the argument shape then differs between models | |
| Impute and disclose | Carry-forward for binary, linear for continuous, invented values in diagnostics. Two defensible rules measured 10.48 apart on scale 35.32 | |

**User's choice:** Refuse only when gaps exist (recommended).
**Notes:** Derived during the turn and recorded rather than asked — every accepted NP case then has
grid == caller rows, so `values.len() == ds.len() + horizon` holds on both arms and the MANIFEST's
"one `RegressorArg` shape serves both models" survives without amendment. Also derived: events are
unaffected by gaps, because `event_row(day, …)` computes its value from the day itself, so an
imputed day has a well-defined indicator. Also derived: the gap predicate is necessarily
whole-series, because with lags the sample list is `(n_lags..n_grid)` — every grid row — so a
narrower "gaps inside a lag window" rule collapses to the same predicate.

### Q2 — Is "unread" proven by test or by construction?

| Option | Description | Selected |
|--------|-------------|----------|
| By construction — no grid slot exists | Index regressors by the caller's row in the lag-free observed-row branch; nothing to fill, no rule to choose | ✓ |
| Sentinel fill (NaN) + test | Grid array materialized, imputed slots NaN so a future read fails loudly. Puts a non-finite value inside a training array | |
| Carry-forward fill + the four-rule test | What spike 014 measured, nothing new. "Unread" becomes a test result a refactor can silently invalidate | |

**User's choice:** By construction (recommended).
**Notes:** Spike 014's four-rule bit-identity table still ships as the falsification probe — it now
confirms a structural fact rather than carrying the claim alone.

### Q3 — `mode: multiplicative` sent to `model: neuralprophet`?

| Option | Description | Selected |
|--------|-------------|----------|
| Refuse, naming the limitation | `multiplicative regressors are prophet-only; set mode to "additive"`. A field may be arm-restricted the way `cap` is growth-restricted | ✓ |
| Build multiplicative on NP too | Every field meaningful on both arms. Unmeasured, no oracle, no evidence budget | |
| Accept and ignore the field on NP | Cheapest, nobody blocked. Violates D-11/D-21 outright | |

**User's choice:** Refuse, naming the limitation (recommended).

## Event argument shape on NeuralProphet

Flagged before the options: whichever way this goes, it is a deliberate change to an *existing*
argument's behaviour, and the no-argument invariance gate cannot see it — that gate covers requests
with **no new argument passed**, and `holidays` is not new. Its eight cases contain no
`neuralprophet + holidays` case, because that combination is currently a refusal.

### Q1 — How does a caller send events to `model: neuralprophet`?

| Option | Description | Selected |
|--------|-------------|----------|
| Unblock `holidays` on the NP arm | Drop it from the prophet-only refusal list at `forecast.rs:117-130`. The literal reading of SC3; `HolidayArg` exposes no Prophet-specific knob, so the shape really is identical | ✓ |
| New NP-only `events` field | `events: Option<Vec<HolidayArg>>`, `holidays` keeps refusing with an upgraded message. Changes no shipped behaviour; two names for one shape | |
| `events` on both arms, `holidays` legacy | Unifies vocabulary going forward. Most churn; a deprecation story the phase cannot finish | |

**User's choice:** Unblock `holidays` on the NP arm (recommended).
**Notes:** Consequences recorded in CONTEXT.md — the pinned refusal test inverts into a positive
test, the `door_surface.knobs` row for `holidays` moves from `'prophet only'` to both arms, and the
change must be sequenced so no window of silent acceptance opens. Rated one-way: it removes a
shipped refusal from the published tool surface.

### Q2 — Events on neuralprophet with `n_lags > 0` — in scope?

| Option | Description | Selected |
|--------|-------------|----------|
| In scope, and measured here | Wire the block through `predict_ar_recursive` / `predict_ar_1step` and extend the planted-effect recovery to lags | ✓ |
| Refuse `holidays` on NP when `n_lags > 0` | Ships only what spike 013 proved. Multiplies the refusal predicate | |
| In scope, documented as unmeasured | Cheapest path to the capability. SC3's bar would bind only lag-free while the shipped surface is wider | |

**User's choice:** In scope, and measured here (recommended).
**Notes:** Justified by a measured risk, not caution — spike 014 saw the AR term absorb a smooth
continuous driver (`price` weight collapsed from −0.0493 lag-free to −0.0048 at `n_lags = 7`).
Converts spike 013's "AR paths unmeasured" scope note from a gap into a task.

### Q3 — What does the NP response publish in `components` for events?

| Option | Description | Selected |
|--------|-------------|----------|
| Per-event components + `holidays` roll-up | Mirrors the prophet arm's component keys; per-column contributions already needed for the recovery bar | ✓ |
| One `events` component | The block's scalar forward output. The two arms would disagree on component naming for the same argument | |
| Per-column components | Finest decomposition, matches design columns one for one. Can reach `MAX_HOLIDAY_COLUMNS` entries | |

**User's choice:** Per-event components + `holidays` roll-up (recommended).

## C-08 event-column pricing

Two findings were verified against the tree during this area rather than asserted, and both changed
what the options had to say:

1. All four holiday bounds sit *inside* the `"prophet" =>` arm (`forecast.rs:192-315`), so the NP
   arm inherits none of them today.
2. `design_cells` is computed on `ds.len()` (`forecast.rs:303`), while the NP event design is built
   over the imputed grid (`span_days`).

A third was found while enumerating hosts: there is no `aprender-mcp-forecast-lambda`, and only
`chronos-forecaster` is deployed (pmcp.run), which is a different door.

### Q1 — Which host is "the deployment target"?

| Option | Description | Selected |
|--------|-------------|----------|

| Deploy to pmcp.run and measure there | A real host with a real network path. Forecast is not deployed there; Phase 6 put deployment in Deferred Ideas | |

**Notes:** Recorded in CONTEXT.md as an explicit reading of SC4 so a verifier does not fail a
criterion no host can currently satisfy. Measure the per-column slope (µs/step vs E), not the
47.9 s structural maximum. Secondary finding to capture in the same run: C-08's existing
`measured_seconds` was taken on aarch64, so the measurement also says whether the axis is
mis-calibrated for the host that gates the repo.

## Regressor identifiability disclosure

Flagged before the options: the invariance signature hashes the whole `diagnostics` object, so a new
key added *unconditionally* changes every captured baseline and breaks SC2. Whatever ships must be
present only when regressors are passed.

### Q1 — What does the door do about a collinear regressor?

| Option | Description | Selected |
|--------|-------------|----------|
| Report + warn above a threshold | Per-column VIF and condition number in diagnostics; a warning above a contract-owned threshold. Refusing would be wrong — the fit is valid, the coefficient reading is not | ✓ |
| Report, never warn | No threshold to defend. A number the operator must interpret unaided is close to not surfacing it | |
| Refuse above a threshold, opt-out flag | The `allow_long_horizon` shape. Blocks a request whose forecast is correct | |
| Stay silent | Smallest diff. Declines spike 011's one operator-facing recommendation | |

**User's choice:** Report + warn above a threshold (recommended).
**Notes:** Use the condition number or per-column VIF, never a pairwise correlation cutoff — a 0.9
threshold passed `price` (r = 0.759) whose beta is still 5× off. Threshold pinned by spike 011's
fixtures, which carry a known-bad column (`discount`, r = 0.999) and two known-good ones.

### Q2 — Where do the numbers surface?

| Option | Description | Selected |
|--------|-------------|----------|
| Inside `diagnostics`, key absent when unused | Baselines untouched, SC2 unamended, and the gate sees future changes for free because `diagnostics` is already hashed | ✓ |
| Top-level `warnings` on `ForecastResponse` | The Chronos door's shape; more discoverable. Sits outside the six hashed fields, so SC2's field set would have to be extended | |
| Both — numbers nested, warnings top-level | Best ergonomics. Two mechanisms to keep consistent, and still forces the signature change | |

**User's choice:** Inside `diagnostics`, key absent when unused (recommended).

### Q3 — Does the diagnostic extend to the neuralprophet arm?

| Option | Description | Selected |
|--------|-------------|----------|
| Prophet only; document the AR caution | VIF is a property of the design matrix Prophet builds. Spike 014's number is "illustrative of the magnitude, not a bound" — nothing to calibrate against | ✓ |
| Both arms, VIF over the NP feature columns | Symmetric responses. AR absorption is a training dynamic, not column collinearity — a green VIF would reassure about the wrong thing | |
| Both arms, with an NP-specific absorption warning | Targets the measured mechanism. An uncalibrated heuristic that would fire on every continuous regressor with lags | |

**User's choice:** Prophet only; document the AR caution (recommended).
