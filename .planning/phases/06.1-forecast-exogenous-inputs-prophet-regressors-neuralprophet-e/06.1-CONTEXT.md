# Phase 06.1: Forecast exogenous inputs — Prophet regressors, NeuralProphet events, and tier-safe cost bounds - Context

**Gathered:** 2026-09-20
**Status:** Ready for planning

<domain>
## Phase Boundary

An operator can supply the information the forecast models cannot infer — known future events
and numeric drivers (price, promotions) — through the **same one stateless `forecast` door**,
with:

- Prophet external regressors proven to Python Prophet 1.4.0 parity on committed fixtures,
- NeuralProphet events trained as an additive block on the f32 autograd,
- every unsupported combination refused rather than silently ignored,
- the NeuralProphet training-cost bound carrying an event-column term that is **measured**, and
- every existing deployed result reproducing **byte-identically** when no new argument is passed.

**In scope:** `RegressorArg` on both model arms; events on the neuralprophet arm; the C-08
event-column cost term and its calibration; the gappy-series regressor rule; the no-argument
bitwise invariance release gate; the identifiability diagnostic; the contract rows all of the
above force (`door_surface.knobs`, `door_surface.cost_axes`, constants, falsification tests).

**Out of scope (new capabilities, each its own phase):** turning any bound into a tier-resolved
profile (that is Phase 7); a Lambda or pmcp.run deployment of `aprender-mcp-forecast`; `model:
auto` routing; country holiday calendars; `freq` H; NeuralProphet quantile regression or
`n_forecasts > 1`; multivariate/covariate inputs.

## Implementation Decisions

### Transcribed from `.planning/spikes/MANIFEST.md` — the `forecast-exogenous-inputs` requirements

These are the user's seven binding decisions from the spike sessions, carried in verbatim. They
are not re-openable by research or planning.

- **D-19: Byte-identical when the new arguments are absent.** Every committed pre-change fixture
  must reproduce its `ForecastResponse` exactly after the plumbing lands. This is the consumer's
  acceptance gate (Forecast Coach, CR constraint 1, 2026-09-20), not a nice-to-have.
  — **Reversibility:** one-way — the consumer bumps a pinned git tag and rebuilds `--locked`
  against deployed results; breaking it invalidates their production output with no migration path.

- **D-20: No new required arguments.** Every new field is `Option<_>` with a serde default;
  `#[serde(deny_unknown_fields)]` stays exactly as it is.
  — **Reversibility:** one-way — `ForecastArgs` is the published tool schema; a required field
  breaks every existing caller at the transport layer.

- **D-21: Errors, not silence.** An unsupported combination (a driver on a model that cannot use
  it) is refused at the door with a message naming the limitation. This is the existing D-11
  pattern, and the worst failure class at this door is the caller getting a plausible answer to a
  question they did not ask.

- **D-22: One `RegressorArg` shape serves both models** — the caller sends one argument to
  `prophet` and `neuralprophet` alike. **This requirement survives intact** under D-26 below: every
  accepted NeuralProphet case has grid == caller rows, so `values.len() == ds.len() + horizon`
  holds on both arms without amendment.

- **D-23: The correctness bar for regressors is parity with Python Prophet 1.4.0**, measured by
  extending the existing rung ladder (data prep → predict-at-Python-params → components), not by
  self-consistency.

- **D-24: One tag per release.** The consumer bumps one line plus the lock entry and builds
  `--locked`.

- **D-25: The public entry point is `forecast(&ForecastArgs)`.** `fitted_forecast` does not exist
  at HEAD or at the consumer's pinned tag `aprender-forecast-v0.63.0` (`fdf6b1802`) — the change
  request named an API the crate does not ship. Do not add it.

### NeuralProphet regressors: scope and the gappy-series rule (SC5)

- **D-26: Regressors are refused on the neuralprophet arm only when `n_lags > 0` AND the series
  has missing days** in `[first, last]`. A gap-free daily series with lags keeps working — the
  imputed grid equals `ds`, so there is no invented value to argue about. The refusal message names
  the gap (count and first missing date) and states the fix. Spike 014's ranked #1, consistent with
  D-11/D-21: refuse rather than default.
  Rejected: refuse whenever `n_lags > 0` (refuses a well-defined case to avoid a cheap check);
  require grid-complete values on NP (would make the argument shape differ between models,
  breaking D-22); impute-and-disclose (two defensible rules measured 10.48 apart on scale 35.32,
  ~30 %, and the garbage probe flipped the sign of both coefficients).
  — **Reversibility:** costly — the predicate is part of the published refusal surface and has a
  `door_surface.knobs` row plus e2e string-matched refusal cases.

  **The gap predicate is whole-series, and that is not a simplification.** With `n_lags > 0` the
  training sample list is `(n_lags..n_grid)` — *every* grid row, imputed included — so any gap
  anywhere enters the loss. A narrower "only gaps inside a lag window" rule collapses to the same
  predicate.

- **D-27: The lag-free imputed-day value is proven unread BY CONSTRUCTION, not by test.** Do not
  materialize a grid-shaped regressor array. Index regressors by the caller's row when assembling
  the observed-row sample list (`np.rs:597`'s lag-free branch already filters to `grid_observed`),
  so an imputed day has no regressor slot to fill and no fill rule to choose. Spike 014's four-rule
  bit-identity table (linear / zero / carry-forward / garbage `1e3`) still ships as the
  falsification probe — it now confirms a structural fact rather than carrying the claim alone.
  Rejected: sentinel NaN fill (puts a non-finite value inside a training array, against the door's
  finiteness guarantees); carry-forward fill + the four-rule test alone (a later refactor that
  starts reading the slot goes green until someone re-derives the probe).

- **D-28: multiplicative regressors are refused on the neuralprophet arm** — a regressor carrying
  `mode: multiplicative` sent to `model: neuralprophet` is rejected, naming
  the limitation (`multiplicative regressors are prophet-only; set mode to "additive"`). NP-lite
  has no multiplicative composition path — spike 013's block is one additive `.add()` on
  `NpModel::forward`, and multiplicative event mode was explicitly not built. A field may be
  arm-restricted the way `cap` is growth-restricted without breaking D-22.
  Rejected: building multiplicative on NP (unmeasured, no oracle, no evidence budget in this phase);
  accepting and ignoring the field (violates D-21 outright).

### Event argument shape on NeuralProphet (SC3)

- **D-29: `holidays` is unblocked on the neuralprophet arm — one field, both models.** Drop
  `holidays` from the prophet-only refusal list at `forecast.rs:117-130`. This is the literal
  reading of SC3's "the same argument shape the prophet arm already takes": the caller switches
  `model` and changes nothing else. It is semantically honest — a holiday IS an event indicator
  column in both models — and `HolidayArg` exposes no Prophet-specific knob (no `mode`, no
  `prior_scale`), so the caller-visible shape really is identical.
  Rejected: a new NP-only `events` field (two names for one shape); `events` on both arms with
  `holidays` as a legacy alias (a deprecation story this phase has no room to finish).
  — **Reversibility:** one-way — it removes a shipped refusal from the published tool surface;
  re-imposing it would break callers who came to rely on the working combination.

  **This is a deliberate behaviour change on an EXISTING argument, and the invariance gate cannot
  see it.** D-19's gate covers requests with *no new argument passed*; `holidays` is not new, and
  the gate's eight cases contain no `neuralprophet + holidays` case because that combination is
  currently a refusal. The pinned refusal test inverts into a positive test, and the
  `door_surface.knobs` row for `holidays` moves from `'prophet only (refused on the neuralprophet
  arm)'` to both arms. Sequence it so no window of silent acceptance opens.

- **D-30: Events are in scope at `n_lags > 0`, and the recovery bar is MEASURED there.** Wire the
  event block through `predict_ar_recursive` / `predict_ar_1step` and extend spike 013's
  planted-effect recovery to `n_lags > 0`, proving the effect is learned by the block rather than
  absorbed by the AR term. This is a real risk, not a formality: spike 014 measured AR absorbing a
  smooth continuous driver (the `price` weight collapsed from −0.0493 lag-free to −0.0048 at
  `n_lags = 7`). SC3's 10 % recovery bar binds at every configuration that ships.
  Rejected: refusing `holidays` on NP when `n_lags > 0` (ships less than the arm can do, and
  multiplies the refusal predicate); shipping it documented as unmeasured (SC3's bar would bind
  only lag-free while the shipped surface is wider — the shape of claim this project has been
  withdrawing, not adding).

  Spike 013's scope note applies directly: "the AR paths and the interaction between an event block
  and stationarised lags are **unmeasured**." This decision converts that from a gap into a task.

- **D-31: The neuralprophet response publishes per-event components plus a `holidays` roll-up**,
  matching the prophet arm's component keys exactly. One component per event name, summing that
  event's window-offset columns as `w_j · x_j`; the per-column contributions are already required
  for SC3's recovery bar, so the decomposition costs arithmetic already being done.
  Rejected: one `events` component (the two arms would disagree on component naming for the same
  argument, and an operator could not see which event moved the forecast); per-column components
  (a components map that can reach `MAX_HOLIDAY_COLUMNS` entries, and it diverges from prophet's
  per-name grouping).

### C-08 event-column pricing and the holiday bounds the NP arm inherits (SC4)

- **D-32: The "deployment target" for the calibration is the self-hosted X64 CI runner**
  (`[self-hosted, X64, Linux, clean-room]`). **SC4's phrase currently names a host that does not
  exist for this server** — there is no `aprender-mcp-forecast-lambda` (Phase 6 deferred the
  wrappers), and only `chronos-forecaster` is live on pmcp.run, which is a different door. The CI
  runner is the host every existing gate already runs on, so the measurement is reproducible on
  every PR rather than a one-off; and it is a different architecture from the aarch64 spike box,
  which is the substantive half of "not the dev box". **Verifiers must read SC4 against this
  decision, not literally** — no other host can satisfy it inside this phase's boundary.
  Measure the **per-column slope** (µs/step vs E), not the 47.924 s structural maximum; the slope
  is cheap enough to live in CI. Round the coefficient **up** — a door must never under-price.
  Rejected: standing up a Lambda wrapper (a new capability with its own deploy/embed/cold-start
  story — its own phase); deploying to pmcp.run (Phase 6 put deployment in Deferred Ideas as
  "operations, after the crates exist"); this aarch64 box (SC4 rules it out, rightly).

  **Secondary finding to record while measuring:** C-08's existing `measured_seconds: 47.924` was
  taken on aarch64 release. The same run says whether the whole axis is mis-calibrated for the host
  that actually gates the repo.

- **D-33: The holiday validation loop hoists above the model dispatch; the design-cost check
  becomes operand-aware.** All four holiday bounds — `MAX_HOLIDAY_COLUMNS`,
  `MAX_HOLIDAY_DATES` / `MAX_HOLIDAY_DATES_TOTAL`, `MAX_HOLIDAY_DESIGN_COST`,
  `MAX_HOLIDAY_NAME_LEN` — move to one site above dispatch so both arms pay them. The design-cost
  check keeps its single constant but changes operand by arm:
  `(ds.len() + horizon) × columns` on prophet, `(span_days + horizon) × columns` on neuralprophet,
  because the NP event design is built over the imputed grid. Same ceiling, two operands; a gappy
  NP series is refused earlier, which is correct because it genuinely costs more.
  Rejected: a separate `MAX_NP_EVENT_DESIGN_COST` (a second constant, row and re-derivation
  whenever either moves); inheriting the prophet operand verbatim (knowingly under-prices the gappy
  NP case by `span/len` — closing one under-pricing while opening another).

  **CLAUDE.md Verification Discipline rule 4 applies and is not optional here:** extending a
  guard's SCOPE requires re-mutating in the new scope. `cost_bounds_match_contract` and the
  position tests must be re-mutated against the NP arm; the old proof does not transfer.

- **D-34: The event-column term is recorded as its own contract constant with the shape kept
  separate.** One new constant (`fit_np_event_cost_per_column`) carries the calibrated, rounded-up
  number, mirrored by a Rust constant the way every other bound is. C-08's `formula:` string
  carries the **shape** — the term is linear in E and additive to the existing product — and a
  `calibration:` note beside it records host, date, commit and method. Phase 7 then swaps the
  constant per tier without re-deriving the shape, which is exactly what the roadmap asked for.
  Rejected: a per-host calibration block (that is Phase 7's mechanism built here under another
  name; this phase's accepted cost is explicitly "the term lands on a hard constant and is
  re-expressed as tier policy in Phase 7"); folding it into `MAX_NP_TRAIN_COST`'s derivation
  (Phase 7 would have to re-derive the shape — precisely what the roadmap told this phase to
  prevent).

### Regressor identifiability disclosure

- **D-35: Report per-column VIF and the design condition number; warn above a contract-owned
  threshold; never refuse.** Refusing would be wrong: spike 011 measured the fit as valid and the
  objective at or better than Python's (slack −3.42 against a one-sided 0.5 bar) even where the
  coefficient was 4.7× off. It is the coefficient's *interpretation* that is unreliable, so the
  honest move is to say so rather than to block. The threshold is contract-owned and pinned by
  spike 011's fixtures, which carry a known-bad column (`discount`, r = 0.999 against
  `yearly_delim_4`) and two known-good ones (`promo`, `weather`).
  **Use the condition number or per-column VIF, never a pairwise correlation cutoff** — a 0.9
  threshold passed `price` (r = 0.759) whose beta is still 5× off.
  Rejected: report-without-warning (a number the operator must interpret unaided is close to not
  surfacing it); refuse-with-opt-out (blocks a request whose forecast is correct); silence
  (declines spike 011's one operator-facing recommendation).

- **D-36: The numbers live inside `diagnostics`, and the key is ABSENT when no regressors are
  passed.** A `regressors` array under `diagnostics` — one object per regressor carrying name,
  mode, mu, std, VIF and an optional warning — plus the design condition number. Absence when
  unused is what keeps D-19 intact: the invariance signature hashes the whole `diagnostics` object,
  so a key added unconditionally changes every captured baseline and breaks SC2. Because
  `diagnostics` is already hashed, the gate sees any future change to these numbers for free with
  no new field to remember to add to `signature()`.
  Rejected: a top-level `warnings` field (sits outside the six fields the signature hashes, so
  SC2's field set would have to be extended and every baseline re-reasoned — and a misfiring
  `skip_serializing_if` emits `"warnings": []` on every response and breaks the consumer's byte
  comparison); both mechanisms (two places to keep consistent, and still forces the signature
  change).

- **D-37: The identifiability diagnostic is Prophet-arm only.** VIF and the condition number are
  properties of the design matrix Prophet builds. On the neuralprophet arm, state the
  AR-absorption caution in the tool description and README — a continuous driver competes with the
  AR term at `n_lags > 0` — and compute nothing. This is honest about what is measured: spike 014's
  number is one series, one gap pattern, explicitly "illustrative of the magnitude, **not a
  bound**", so there is nothing to calibrate a threshold against.
  Rejected: VIF over the NP feature columns (AR absorption is a training dynamic, not column
  collinearity — a green VIF would reassure about the wrong thing); an NP-specific absorption
  warning (an uncalibrated heuristic that would fire on every continuous regressor with lags).

### Spike-measured, NOT re-decidable

Research and planning must treat these as settled. Each was measured; re-litigating one costs the
phase its evidence base.

- **Column order:** seasonalities → holidays (sorted by the generated `{name}_delim_{±off}` string)
  → extra regressors in **insertion** order. Verified identical to Python at 24 and 30 columns.
  Regressors **append**; no existing column index moves. This is what makes D-19 free.
- **Standardisation is pandas `Series.std()`, ddof = 1** — numpy's default ddof = 0 is a silent
  0.17 % shift in every coefficient. Under `standardize = "auto"`, a column whose unique values are
  exactly `{0, 1}` is **not** standardised (`mu = 0, std = 1`). Computed over **history rows only**;
  on the NP arm, over the **observed train rows**.
- **Splice onto the shipped `Design`** — a 219-line additive change. `Design` has every field
  `pub`; the optimiser and gradient need no change. **Do not fork or rewrite `prophet.rs`.**
- **`predict` is the signature change, not `feature_row`.** `feature_row` keeps filling the
  seasonality and holiday cells unchanged; the regressor cells are written *beside* the row from
  the caller's array, so `predict` needs a per-row value channel.
- **`s_a` / `s_m` / `prior_scales` come out exact `0.0`** against the oracle.
- **Two roll-up components Prophet publishes by name:** `extra_regressors_additive` (scaled by
  `y_scale`) and `extra_regressors_multiplicative` (**not** scaled).
- **The components bar binds RELATIVE to `y_scale`, not the absolute 1e-10.** On `retail_sales`
  (y_scale 518 253) the absolute bar passes with only 3× headroom and would start failing for
  arithmetic reasons.
- **A coefficient disagreement is not a defect until the objective control says so.** Rust's
  `price` beta came out 4.7× from Python's, at objective slack −3.42 — Rust found a *better*
  optimum. Always run the objective control before calling a beta wrong.
- **Events compose as one additive `Linear(E, 1)` block beside `NpModel`** — one `.add()` on
  `forward()`, both parameter sets handed to one `AdamW`. Do not fork `NpModel`. Block init mirrors
  the seasonality block's `std = (1/dim).sqrt()` scaling.
- **Event indicator columns reuse the Prophet expansion** — one column per `(event, window offset)`,
  events in insertion order, offsets ascending within an event, with one membership set hoisted per
  event out of the row loop. This is what makes D-29's one-argument-two-models claim literal.
- **Event cost is LINEAR in E** (`µs/step ≈ 12.9 + 0.085·E` on the spike box). The shape transfers;
  the constant does not (D-32).
- **The tape does not grow with the event-column count** — 25 ON / 20 OFF, a fixed +5, so
  `clear_graph()` still empties it and there is no leak.
- **Determinism is checkable:** seed 42 twice is bit-identical; **seed 43 differs**, so the check
  can fail.
- **The invariance signature EXCLUDES `fit_seconds` and `predict_seconds`** (wall-clock — including
  them makes the gate vacuous in the opposite direction) and hashes f64s by **`to_bits()`** with
  `-0.0` normalised (a formatted comparison silently accepts any change below print precision).
- **The mutation proof is not optional.** A green invariance table with no falsification probe
  beside it is indistinguishable from a broken harness.
- **`freq != "D"` is already refused on the neuralprophet arm** (`forecast.rs:421-423`, pinned by
  `neuralprophet_refuses_non_daily_freq`). This answers the change request's P5 Q3 and voided spike
  014's original premise — do not plan a weekly/month-start grid mapping.
- **Never linearly interpolate a binary driver** anywhere in the pipeline: it produces a "0.5 promo"
  day, which is not a thing that happens.
- **Core's `SmoothL1Loss` is detached from the graph** — build Huber from ops (`weighted_huber`,
  already public). Carried from spike 002 / D-10.
- **The fixture CSVs quote their fields** (`"2007-12-10"`); strip quotes before parsing or the date
  validator refuses the row. Sort by `ds` and de-duplicate at load — `wp_log_R.csv` is not
  chronological.
