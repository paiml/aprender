## Deviations from Plan

### 1. [FINDING A — plan contradiction] Verify t1c is unsatisfiable by construction, and already was before this plan

t1c asserts `grep -c '#\[ignore' crates/aprender-forecast/src/invariance.rs` is **0**. Wave 1
deliberately shipped `capture_baseline` as `#[ignore]` *plus* `INVARIANCE_BASELINE_MODE=capture`
— a capture that can run by accident overwrites the evidence it exists to preserve, and
without the `#[ignore]` its env-gate assertion would make the suite permanently RED.

**Measured, not assumed, that this pre-dates the plan:**

```
git show HEAD:crates/aprender-forecast/src/invariance.rs | grep -c '#\[ignore'   -> 2
```

at wave-1 HEAD (`4983ffafe`), before a single line of this plan existed. The count is 3 now
only because this plan's module rustdoc *mentions* `#[ignore]` in prose.

The verify's own `fails_when` states the intent: "any ignore attribute in this module means
part of the release gate is unreachable from a plain test run". The **capture is not part of
the release gate** — it is the tool that produces the baseline the gate reads. So the intent
is satisfiable; the grep is over-broad. The plan's *acceptance criterion* ("Neither part-A
test carries an `#[ignore]` attribute") is met exactly.

**Substitute run, and green:** a python probe that counts `#[ignore]` in ATTRIBUTE position
only, resolves the function each one decorates, and requires exactly one — on
`capture_baseline`. Output: `attribute-position #[ignore] count: 1 / #[ignore] on fn capture_baseline`.
This is strictly stronger than the grep for the property that matters: it would go RED on an
`#[ignore]` added to any assertion, which the raw count cannot distinguish.

Deleting `#[ignore]` from `capture_baseline` to make the literal verify pass was rejected: it
would make a destructive capture runnable by accident and turn the suite red.

### 3. [FINDING C — defect in the plan's own t2c probe, found by mutation and not by reading]

t2c carries a python probe that extracts each test body and looks for `consts::ARCH` or
`#[ignore`. I wrote a Rust twin of it into the module (`parts_a_and_b_are_unconditional`, an
artifact the plan names). Running the guard's case table as mutations — CLAUDE.md Verification
Discipline 4 and 7 — found **two blind spots, both shared with the plan's python**:

1. **The body is anchored at `fn <name>`, but `#[ignore]` sits BEFORE `fn`.** So an
   `#[ignore]` on part A is outside the extracted region entirely.
2. **`find("fn " + name)` prefix-matches a renamed function**, so `part_a_..._door` silently
   resolved to `part_a_..._doorX` and the MISSING direction never fired.

**Measured, side by side, on a tree carrying `#[ignore = "slow"]` on part A:**

```
--- the PLAN's t2c python probe ---
parts A/B that are arch-conditional or ignored: []
plan-probe rc=0                                     <-- GREEN on a gated part A

--- the in-tree Rust twin ---
rust-twin rc=101
part_a_every_case_is_deterministic_through_the_door carries an ignore attribute, so part
of the release gate is unreachable from a plain `cargo test --lib` run
```

Fixed in the Rust twin only (the verify body stays byte-for-byte verbatim): the extraction
walks back to the preceding `#[test]`, asserts the walk-back did not cross another function,
and matches `fn {name}(` with the parenthesis. The full five-case table now fires; positive
control green.

**This is the finding to carry forward.** t2c is the verify that exists to stop a
cross-platform red being silenced by relaxing parts A and B, and as written it cannot see the
single most likely way that would be done — adding `#[ignore]`. The in-tree Rust test is now
the real guard; the python is a weaker duplicate of it. A later plan editing that verify
should replace its body with `cargo test … invariance::parts_a_and_b_are_unconditional`
rather than re-deriving the extraction.

### 4. [Rule 2 — missing critical assertion] Part C needed a band non-vacuity check the plan did not ask for

Part C compares `yhat_lower` and `yhat_upper` bit for bit. Two *degenerate* bands — identical
because both are zero-width — would satisfy that comparison without the band path ever having
produced anything. Added: an assertion that the band has non-zero width at some index on every
series. Same class as the plan's own component-count floor.

### 5. [Observation, not fixed] `the_signature_detects_a_one_ulp_change` is now a strict subset of part B

Wave 1's in-plan floor covers `yhat[0]`, `trend[last]` and the extra `components` key — shapes
1, 2 and 3 of part B — and its own doc comment says "Plan 06.1-04 owns the full mutation
ladder". It is kept: removing a committed wave-1 test is outside this plan's scope, and its
cost is measured below at effectively zero on the critical path. Flagged for whoever next
touches the module.

## Suite cost — the deferred item's measurement obligation

The plan deferred a review concern about suite time with an explicit obligation: *record the
module's wall time in the SUMMARY and raise it as a finding if it is material.* Measured on
this box (M4 Pro, `--lib`, `aprender-forecast` at `opt-level = 3`, same session, warm build),
by checking out the wave-1 file and running both:

| | before (wave-1 `4983ffafe`) | after (this plan) | delta |
|---|---|---|---|
| `invariance::` module | 19.70 s, 3 passed | 39.79 s, 9 passed | **+20.1 s** |
| whole crate `--lib` | 34.71 s, 139 passed | 41.14 s, 145 passed | **+6.4 s** |

Per test, run alone: **part A 41.98 s**, part B 1.61 s, part C 1.85 s.

**Reading it honestly.** Part A is ~99 % of the added cost, and it is irreducible without
weakening the claim: determinism over eight cases means sixteen door calls. Parts B and C
cost ~3.5 s combined and are hidden entirely by libtest's parallelism — the module wall time
(39.8 s) is essentially part A alone, and the crate's `--lib` critical path is now the
invariance module.

**Not material enough to be a finding, on this measurement.** +6.4 s on a 41 s crate suite is
inside the budget the crate already runs at, and the alternative posture — splitting or
`#[ignore]`-ing part of the gate — is precisely what this phase exists to close (CONTEXT.md's
recorded finding is that the one harness watching an axis could only be reached with an
explicit flag). Recorded so a future +N is measured against a real baseline rather than
guessed.

## The part-B fixture suggestion, considered and NOT applied

The suggestion on record: `the_signature_detects_a_one_ulp_change` rebuilds the 2905-point
peyton case only to obtain a response to perturb, and a 293-row fixture would prove the same
property far more cheaply. **Not applied, for a measured reason rather than a preference:**

- The peyton rebuild costs **1.61 s** and runs in parallel with part A's 41.98 s, so the
  saving on the module's wall time is **~0 s**. The stated benefit does not exist here.
- Part B's mutation 6 requires a REAL door response with a populated `diagnostics.lbfgs`
  sub-object — it steps `objective` by one ULP and flips `budget_hit`. A synthetic fixture
  would have to fabricate that object, which turns "the signature hashes what the door
  actually produces" into "the signature hashes what the test fabricated". That is a weaker
  property, and mutation 6 is the only thing proving `diagnostics` is hashed at all.

Part B uses `retail_sales` (293 rows) for the two *cheap* companion properties — the
wall-clock exclusion and the negative-zero normalisation — where no populated `diagnostics`
leaf is needed. So the cheap fixture is used exactly where it costs nothing.
