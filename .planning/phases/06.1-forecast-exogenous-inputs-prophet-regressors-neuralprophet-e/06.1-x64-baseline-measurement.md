# X64 invariance baseline — measurement for the 06.1-05 checkpoint

**Status:** data obtained; NOT yet committed into `invariance_baseline.json` (see Finding 3).
**Measured:** 2026-09-21, by the phase orchestrator, before wave 3's checkpoint.

## Why this was not done on the self-hosted runner

Checkpoint options (a) and (b) both require the self-hosted X64 runner. Measured:

- `gh api repos/guyernest/aprender/actions/runners` -> `total_count: 0`. The fork has no
  self-hosted runner registered.
- The only `runs-on:` in `.github/workflows/ci.yml` is `[self-hosted, X64, Linux, clean-room]`,
  so no job in that workflow can run on the fork at all.
- That job's container is `localhost:5000/sovereign-ci:stable` — a registry local to the
  runner — so the CI container cannot be reproduced on any other host either.

Operator authorised an EC2 substitute. For THIS measurement EC2 was not used, because the
question is bitwise, not timing: emulated `linux/amd64` executes the same instruction
semantics and glibc's `sin`/`cos` are software implementations, so a container answers it
exactly and for free. EC2 remains the right host for the C-08 **timing** slope, which
emulation would distort.

## Method

`INVARIANCE_BASELINE_MODE=capture cargo test --locked -p aprender-forecast --lib
invariance::capture_baseline -- --ignored --nocapture`, run in `--platform linux/amd64`
containers on an aarch64 macOS host. rustup auto-installed the repo-pinned
`1.93.0-x86_64-unknown-linux-gnu` in every container, so rustc version is held constant and
only arch + libc vary.

prudent: a single-architecture baseline compared across hosts would go red on all eight
cases in CI, and the obvious reading of that failure — "the splice broke invariance" —
would be entirely wrong.

## Finding 2 — the x86_64 value is host-STABLE, so the divergence is purely architectural

Two controls, both all-eight-identical:

- **libc**: Debian 12 glibc **2.36** vs Debian 13 glibc **2.41** — identical signatures.
  Several years of libm changes move nothing here.
- **commit**: `bfc21cbd9` (the pre-splice capture state) vs `7a982a370` (HEAD, after waves
  1 and 2) — identical signatures.

Also checked: no `RUSTFLAGS`, no `target-cpu`/`target-feature` in `.github/workflows/ci.yml`
or `.cargo/config.toml`, and `[profile.dev.package.aprender-forecast] opt-level = 3` is
pinned in the workspace manifest. So the x86_64 value is determined entirely by inputs this
repo pins, which is what makes it safe to commit a value obtained off-runner.

**Bonus, nobody asked for it:** the commit control is an independent cross-architecture
confirmation of SC2. D-19 invariance holds on x86_64 across every change waves 1 and 2 made,
not just on the aarch64 host where the gate has been running.

## Finding 3 — `capture_baseline`'s guard makes its own documented workflow IMPOSSIBLE

`invariance.rs:375` refuses to capture a second architecture unless
`HEAD == captured_at_commit` (`c850e62aa`):

> this baseline describes commit c850e62aa…, but HEAD is …; check out c850e62aa before
> capturing another architecture, or the two halves of the file would describe different trees

The intent is right — the two halves must describe one tree. But **`invariance.rs` does not
exist at `c850e62aa`** (`git ls-tree c850e62aa` — absent; it was added by `bfc21cbd9`). So
the harness cannot run at the only commit the guard accepts. Meanwhile 06.1-05's checkpoint
instructs the operator to "run the baseline capture entry point on that runner at the CURRENT
commit" — which the guard rejects by construction. The two directions contradict.

It is satisfiable only by reconstructing wave 1's *uncommitted* state: check out `c850e62aa`,
then add `invariance.rs` and its `mod` line as working-tree changes so `git rev-parse HEAD`
still reports `c850e62aa`.

Verified the guard is otherwise sound: it refused **before writing**, so
`invariance_baseline.json` is byte-unmodified after three failed capture attempts.

**Recommended fix (for whoever owns it):** compare the *computation* tree rather than the
commit id — the harness is `#[cfg(test)]` and cannot affect a signature. `bfc21cbd9` differs
from `c850e62aa` only by `invariance.rs`, its fixture, and a `#[cfg(test)] mod invariance;`
line in `lib.rs` (verified by `git diff --name-only`), which is why capturing there is
legitimate and produced the same values as HEAD.

## What is NOT claimed

These signatures were produced in emulated containers on an aarch64 host, **not** on the
self-hosted runner and **not** in `sovereign-ci:stable`. Finding 2 is the evidence that this
should not matter; it is not a proof that it does not. If upstream CI disagrees when this
branch reaches it, the entry is wrong and that is worth learning immediately — strictly
better than a gate that skips forever and reports nothing either way.

SC4's coefficient half is untouched by all of this and still requires the C-08 timing sweep.
