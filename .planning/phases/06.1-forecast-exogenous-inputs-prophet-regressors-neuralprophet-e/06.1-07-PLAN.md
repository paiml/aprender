<objective>
Finish D-22 by making the one `RegressorArg` shape actually work on the neuralprophet arm, and
decide the one thing this phase owns that nothing else could: what happens when a regressor
meets an imputed daily grid.

Purpose: NeuralProphet trains on a daily grid denser than the caller's rows. Lag-free it never
reads an imputed day's regressor value — all four fill rules including a deliberate garbage
probe are bit-identical. With lags it reads every one of them, and two DEFENSIBLE rules
measured 10.48 apart on a series of scale 35.32, about 30 percent, while a wrong value on 12
percent of grid days flipped the sign of both coefficients. The change request's contract left
those values undefined. This plan refuses that case by name and makes the lag-free guarantee
structural rather than test-borne.

Output: the by-construction indexing, the gap refusal, the multiplicative refusal, and the
four-rule probe kept as a falsification probe beside a structural fact.
</objective>

The lag-free branch of `train`'s sample list already filters to `grid_observed`. Carry, beside
that sample list, a parallel index from each selected grid row back to the CALLER's row, and
read the regressor value at that caller index. An imputed grid day is never selected on this
branch, so it has no regressor slot to fill and there is no fill rule to choose. Do not build a
grid-length regressor vector and then filter it: building it is what creates the undefined
values, and a later refactor that starts reading the slot would go green under a test-only
guarantee. The spike prototype builds one; deliberately do not port that part, and say why in
the code comment.

For the lagged branch, the sample list is every grid row from the lag count onward, so a
caller-row index does not exist for every sample. That case is REFUSED by Task 2 when the
series has gaps, and when the series is gap-free the grid rows and the caller rows coincide
one for one, so the same caller-row index is total.

**Assert that coincidence with a RELEASE-MODE guard that returns an error, not with a
`debug_assert!`.** `debug_assert!` is compiled out of `--release`, which is the profile the
door ships in, so the earlier draft's `debug_assert_eq!(n_grid, n_train)` would be absent
exactly where it matters: if D-26's predicate ever regressed, the release door would index a
shorter caller array out of bounds — a PANIC on caller data, which contradicts the door's own

the invariant, placed on the lagged-with-regressors path before the first index. `Internal`, not

server-side invariant break and the pmcp mapping should say so.

(`np.rs:611`) stays as it is — that one is on the hot path, is a pure internal consistency

**Specify the learned block, its optimiser ownership, its retained state and the `prior_scale`
semantics — all four, because a field the door ACCEPTS and the trainer IGNORES is the D-21
failure this phase exists to prevent.** The earlier draft described indexing and adding
contributions without saying who owns the parameters:

- **The block.** Numeric regressors compose exactly as the event block does (plan 06.1-05):
  one additive `Linear(R, 1)` without bias beside `NpModel`, its weight initialised from the
  crate's `Rng` scaled by the square root of one over `R`, and ONE `.add()` on the forward.
  Do NOT fold regressors into the event block's columns: the two have different standardisation
  (events are 0/1 indicators, regressors are ddof-1 standardised continuous columns) and
  different refusal surfaces, and sharing one `Linear` would make the event recovery bar and
  the regressor behaviour inseparable.
- **Optimiser ownership.** The block's parameters are extended into the SAME `parameters_mut`
  vector handed to the one `AdamW`, beside `NpModel`'s and the event block's. Assert it the way
  plan 06.1-05 does: a test that the regressor weights CHANGE across one optimiser step. A
  block built but not registered contributes to the forward pass and never learns.
- **Retained inference state.** The `Standardized` list (name, `mu`, `std`, mode) and the
  learned weights travel together with the model to the predict paths, because a future row's
  contribution needs the SAME `mu`/`std` the training rows used. Put them in `TrainLog` beside
  the event weights so the predict paths and the tests read them from one place.
- **`prior_scale` on this arm: REFUSE IT, do not silently ignore it.** The NP trainer has ONE
  global `weight_decay` (`forecast.rs:480`, `weight_decay: 1e-3`) and no per-parameter prior;
  there is no mechanism by which a per-regressor `prior_scale` could take effect, and no
  measurement in any spike for what it should mean here. Accepting the field and dropping it
  is exactly the "plausible answer to a question they did not ask" failure D-21 names. So: a
  regressor carrying an explicit `prior_scale` sent to `model: neuralprophet` is REFUSED,
  naming the limitation (`prior_scale is prophet-only; the neuralprophet trainer applies one
  global weight decay and has no per-regressor prior`) and the fix (omit the field, or use

  Record this in the `prior_scale` knob row's `arms:` text alongside `mode`'s
  multiplicative restriction; it is the same shape of arm restriction D-28 already establishes.

Extend `np::predict_ts`, `np::predict_ar_1step` and `np::predict_ar_recursive` to add the
standardised regressor contribution for the rows they predict, indexed by the caller's row for
history rows and by the horizon offset for future rows.
