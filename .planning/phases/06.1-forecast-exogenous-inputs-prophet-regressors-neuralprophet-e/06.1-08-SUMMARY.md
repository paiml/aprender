### Task 1 — the four caller-facing surfaces (`20fa6f5c9`)

Both crate READMEs gained, in the structure each already used:

- **`regressors`** — the field, all five `RegressorArg` sub-fields, the length contract
  (`len(values) == len(ds) + horizon`, exactly), insertion order as load-bearing (and why a
  name-keyed map was rejected: `serde_json::Map` is a `BTreeMap` and iterates key-sorted),
  the `10.0` default prior scale, and Prophet's auto-standardisation rule including the
  `{0, 1}` binary carve-out and the pandas ddof = 1 detail.
- **`holidays` on both arms** — stated in the terms a caller cares about (switch `model`,
  change nothing else) with the component keys each arm publishes named: prophet emits one
  component per holiday NAME plus a `holidays` roll-up; neuralprophet emits the same,
  grouped by name rather than by column or index, and requires `n_lags = 0`.
- **Every refusal this phase added**, as a table of *limitation* / *fix* pairs: the length
  tie, non-finite values, an unknown mode, a prior scale outside `[1e-153, 1e150]` (with the
  real consequence stated — L-BFGS runs zero iterations and the regressor contributes exactly
  nothing while the response still looks normal), a duplicate name, a name colliding with a
  generated column or a reserved response key, an over-long name, a constant column, the
  count ceiling, the design-cost product, multiplicative mode on the NP arm, `prior_scale` on
  the NP arm, and a regressor on a gappy series at `n_lags > 0`.
- **The `diagnostics.regressors` report** — what each field means, that the keys are ABSENT
  (not `null`, not `[]`) when no regressor is sent and why the mechanism has to be "the key is
  never constructed", that a warning is about the *coefficient's attribution* and not about
  `yhat`, and that holiday indicator columns are outside the diagnostic's column set with the
  `scope` string saying so and the `O(n*K^2 + K^3)` reason why.

**`TOOL_DESCRIPTION` was the surface that mattered most.** As found, it already mentioned
`regressors` and both-arm `holidays` (an earlier wave had updated it) but carried none of the
three arm restrictions and none of the AR-absorption caution — and D-37 names the tool
description specifically. The constant, and only the constant, was edited: the wiring, the
builder chain and `map_error` are untouched, and the D-16 band-honesty closing sentence
survives verbatim.

**The AR-absorption caution now exists in four places** — both READMEs, the `n_lags` and
`RegressorArg.values` doc comments (which `schemars` lifts into the advertised input schema),
and `TOOL_DESCRIPTION`. All four say the same thing and scope it the same way: a continuous
driver competes with the AR term at `n_lags > 0`; the measured collapse to **-0.0048** from
**-0.0493** lag-free is *illustrative of the magnitude and explicitly not a bound* (one series,
one gap pattern); and no VIF or condition number is computed on that arm because AR absorption
is a *training dynamic* rather than column collinearity, so a green VIF would reassure about
the wrong thing.

The forecast README's opening example was also switched from an exhaustive struct literal to
`..Default::default()`, since the exhaustive form is precisely what breaks on a field addition
— the example was teaching the pattern the compatibility section warns against.

### BLOCKER — the SC2 no-argument invariance gate is RED under the build CI runs

`crates/aprender-forecast/src/invariance.rs:718`,
`invariance::every_baseline_case_reproduces_its_signature`.

```
case peyton/prophet/default on arch=aarch64 no longer reproduces its pre-change signature:
recorded aa669c2352dd376a, got e01f605419765a6a
```

**Deterministic in both directions, not flaky.** Controls, each varying one thing:

| Control | Result |
|---|---|
| `cargo nextest run --profile ci -p aprender-forecast --lib invariance::` | **PASS**, 9/9, repeatable |
| `... --workspace --lib` filtered to this one test | **FAIL**, `e01f605419765a6a` on all 3 retries |
| `-p aprender-forecast --lib` under a saturating 14-core busy-loop load | **PASS** — so it is not CPU load, and not the cooperative `FIT_BUDGET_SECS` |
| `-p aprender-forecast -p aprender-core --lib` | **PASS**, even though `cargo tree -e features` confirms that scope *does* enable `aprender-core` `parallel`/`rayon` — so rayon reduction order is **ruled out** |
| `-p aprender-forecast -p apr-cli --lib` | **FAIL**, identical hash — a one-variable flip |

**Mechanism: cargo feature unification.** `aprender-forecast` depends on `aprender-core` with
`default-features = false`. `cargo tree -e features -p aprender-forecast` resolves **zero**
`aprender-core` features; the same query across the workspace resolves **23** —
`format-compression`, `format-encryption`, `format-homomorphic`, `format-quantize`, `half`,
`safetensors`, `safetensors-compare`, `setfit`, `conformance-fixtures`, `hf-hub-integration`,
`hf-hub`, `dirs`, `ureq`, `sha2`, `aes-gcm`, `argon2`, `hkdf`, `x25519-dalek`, `lz4_flex`,
`zstd`, `parallel`, `rayon`, `default`. `apr-cli`'s default feature set is what pulls most of
them. Narrowing past "somewhere inside apr-cli's defaults" was not attempted because `apr-cli`
does not build with `--no-default-features` on this tree (unresolved `axum` / `realizar`
imports), so that bisect rung is unavailable.

**Why it matters.** The gate exists to prove D-19/SC2 — that a caller passing NO new argument
gets a byte-identical answer, which is exactly what makes the delivery "one pinned line plus a
lock entry". The baseline was captured under a build configuration CI never performs
(`.github/workflows/ci.yml:289` runs `--workspace --lib`), so the guarantee is currently proven
only in a scope neither CI nor a real consumer uses — and under the scope CI does use, the
answer differs.

**Do not close this by re-recording the baseline under `--workspace`.** That inverts which
scope is red without answering either real question: which enabled feature moves the numerics,
and whether a consumer's forecast is supposed to depend on the feature set of unrelated
workspace members at all. Both need their own measurement and their own decision. Recorded as
item 5 of this phase's `deferred-items.md` and as a STATE.md blocker.
