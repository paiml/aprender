**The holiday loop** (`crates/aprender-forecast/src/forecast.rs`, approximately :183-243). Per holiday
it checks window signs, then `|window| <= MAX_HOLIDAY_WINDOW`, then `dates.len() <=
MAX_HOLIDAY_DATES`, then accumulates `holiday_dates_total += h.dates.len();`, then accumulates
`holiday_columns += (h.upper_window - h.lower_window + 1) as usize;` and IMMEDIATELY refuses if
`holiday_columns > MAX_HOLIDAY_COLUMNS`, then parses every date via `parse_date` and pushes a
`Holiday`. The `holiday_dates_total` comparison against `MAX_HOLIDAY_DATES_TOTAL` is at approximately
:245 — AFTER the loop. The comment at approximately :210-211 already claims the running sum "is
refused below the moment the aggregate ceiling is passed"; the fix is to make the code match the
comment, keeping the post-loop check as the one that reports the exact total.

**The holiday column builder** (`crates/aprender-forecast/src/prophet.rs`, `columns`, approximately
:146-165). For each holiday and each offset in `lower_window..=upper_window` it pushes a `Column`
whose `name` is `format!("{}_delim_{}{}", h.name, sign, off.abs())` and whose `component` is
`h.name.clone()` — TWO owned `String`s per column, both derived from one payload occurrence of the
name — and then `hcols.sort_by(|a, b| a.name.cmp(&b.name))`, an `O(C log C)` comparison sort whose
comparisons are byte-wise over those names. With `MAX_HOLIDAY_COLUMNS` at 1 000 that is 2 000 copies
plus ~10 000 string comparisons per request, each scaling linearly in the name length. Nothing bounds
the name length at HEAD. The response's `components` map is also keyed on the name, so the name also
reaches the serialized reply.

**The NeuralProphet arm** (`crates/aprender-forecast/src/forecast.rs`, the `"neuralprophet"` match
arm). It refuses `freq != "D"`, defaults `n_lags` to 0 and refuses `n_lags > 365`, builds
`np::NpData::new(&ds, &args.y, n_train, 10, 0.8)`, refuses `n_lags >= d.n_train_grid`, then runs a
learning-rate sweep: `&[0.03, 0.1]` when `n_lags > 0` and `&[0.01, 0.03, 0.1]` otherwise — TWO or
THREE full `np::train` calls per request — with `epochs: Some(np::auto_epochs(n_train).min(320))` when
lags are on and `None` (i.e. `auto_epochs(n)` computed inside `train`) otherwise. There is NO time
budget anywhere on this path; `fit::FIT_BUDGET_SECS` is read only by `fit::fit_prophet`.

**The training work** (`crates/aprender-forecast/src/np.rs`, `train`, approximately :493-515):
`n_grid = d.n_train_grid`; `samples` is the observed rows when `n_lags == 0` and `(l..n_grid)` when
lags are on; `n = samples.len()`; `batch = cfg.batch.unwrap_or_else(|| auto_batch(n))`;
`epochs = cfg.epochs.unwrap_or_else(|| auto_epochs(n))`; `n_batches = n.div_ceil(batch)`;
`total_steps = epochs * n_batches`. `auto_epochs` (:418-421) is
`(10.0 * (100.0 / n * 2^(2.25 * log10(10 + n))).ceil()).clamp(20.0, 500.0)`. `d.n_train_grid` is the
imputed DAILY grid length, bounded by `MAX_SPAN_DAYS` (20 000), not by `MAX_POINTS`. The AR head is
`ar_layers: vec![32]` when lags are on, so per-sample work scales with `n_lags`.

**The e2e harness** (`crates/aprender-mcp-forecast/src/lib.rs` `mod e2e`): `serve()`, `synth(n)`,
