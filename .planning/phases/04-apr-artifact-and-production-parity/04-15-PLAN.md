<objective>
Close two review findings that no existing plan covered.

**"There is no complete spawned CLI lifecycle proof for OPS-02."** Training, inspect, eval and
predict are each tested in their own plan, but nothing drove the real binary through the whole
chain consuming each command's outputs. Given that the selection-lock workflow now spans two
processes (review B4), that gap is exactly where a wiring defect would hide: every unit test could
pass while `apr eval --split test` cannot read the lock `apr eval --split validation` wrote.

**"Generic APR tooling compatibility is assumed rather than tested."** D-01's entire justification
for canonical tensor names is that `apr tensors/qa/diff` keep working unmodified, and RESEARCH
flags this as assumption A3 — a U8 pseudo-tensor may trip numeric-only assumptions. No plan tested
it. This one does, against a real artifact, through the real binary.

Purpose: OPS-02 at the "a user can" tier, and the first actual evidence for D-01's assumption.

Output: one integration test file. No source changes — if a lifecycle step cannot be completed
through the shipped CLI, that is a finding to surface, not something to patch around here.

Branch: `gsd/phase-4-apr-parity`. Wave 7, parallel with 04-09. HARD CONSTRAINT: this plan creates
exactly ONE file and touches NO Cargo.toml — the file carries a module-level
`#![cfg(feature = "setfit")]` so cargo auto-discovers it and it compiles to an empty test binary
when the feature is off. 04-09 owns apr-cli/Cargo.toml this wave.
</objective>
