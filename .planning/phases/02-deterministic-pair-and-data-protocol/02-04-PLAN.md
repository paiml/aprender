<objective>
Extend the Phase 1 fixture generator to emit RNG-independent SetFit pair-count reference fixtures
from the hash-locked `setfit==1.1.3` environment, recording MEASURED semantics (D-23, Pitfall 1),
alongside a parallel family of Aprender-contracted counts — plus shared typed fixture models and
the Rust-side integrity verifier that is the canonical check.

Purpose: D-22 accepts that pair identities cannot match Python's RNG, so the evidence strategy is
invariant parity: counts, balance, class-correctness, self-pair/orientation facts, and singleton
behavior on hand-enumerable layouts. Plans 02-07 and 02-08 consume these fixtures; without this
plan their "matches the reference" claims would be assertions about documentation the pinned
implementation contradicts.
Output: two committed fixture families + manifest.sha256 + shared fixture models + a Rust verifier.

## Review corrections incorporated (02-REVIEWS.md)

Both reviewers called this the best-isolated plan; the corrections are test-layout repairs, not
design changes.

- **F15 / Codex 02-04 MEDIUM — public structs in one integration test cannot be imported by
  another.** Each file under `tests/` is a separate crate. The typed fixture models move to
  `tests/common/mod.rs`, included with `mod common;` from `reference_fixtures.rs` and later from
  plan 02-07's and 02-08's integration tests. (The repo's alternative precedent is the
  `#[path = "..."]` include used by `crates/aprender-core/tests/setfit_conformance.rs`; the
  `tests/common/mod.rs` idiom is preferred because cargo already treats that path as a module
  rather than a test target.)
- **F15 / Codex 02-04 MEDIUM — `shasum -c` resolves listed paths relative to the CWD, and the
  automated command and the acceptance text assumed different directories.** The Rust verifier
  becomes the canonical, cross-platform check; it resolves every manifest entry relative to the
  manifest file's own directory. `shasum -a 256 -c` is retained only as a documented convenience
  with its required `cd` stated explicitly, and it is NOT the `<automated>` command.
- **F15 / Codex 02-04 LOW — "singleton class → zero positive capacity" was imprecise.** Corrected
  everywhere to "a singleton class contributes zero positive capacity"; `[4,1]` still yields six
  positives from the four-member class.
- **F15 / Codex 02-04 LOW — "additive only" was too restrictive.** Relaxed to an outcome
  condition: the Phase 1 emitted fixtures and their manifest must be byte-identical after the run;
  shared generator helpers may be refactored as long as that holds.
- **F15 / Codex 02-04 suggestion — record the Python environment, not just the package version.**
  Each fixture now records `setfit_version`, `uv_lock_sha256`, and `uv_version`.
- **F15 / Codex 02-04 suggestion — generate into a temp directory and compare before replacing.**
  The generator writes to a temp dir, diffs against the committed tree, and reports the diff;
  replacement is deliberate, so a re-baseline is always a reviewable change.
- **F1 (consequence) — the K≈N adversarial layout gets a contracted fixture here** so plan 02-08's
  capacity gate has a reference row to assert against. A three-class fixture set could never
  expose the O(K²) sampler the review rejected.
