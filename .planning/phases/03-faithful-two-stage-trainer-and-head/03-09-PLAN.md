<objective>
Make canonical test access mechanically earned: a trusted validation evaluator that computes metrics
from the verified artifact and the canonical validation split rather than accepting a caller's
number, a hash-committing SelectionLock that records the whole candidate history and applies the
selection rule itself, and a CanonicalTestToken mintable only from the verified run object whose
artifact hash matches the lock's (D-14 as amended, TRN-07).

Purpose: TRN-07 — selection using canonical validation only, with a selection-lock record created
before canonical test access is permitted. This is the thing Phase 5's "any post-test-selected cell
invalidates the report" hangs off.
Output: evaluate.rs + lock.rs + the transitions + contract growth for the evaluation, lock and token
equations.
</objective>

**Review fix 1 — `ValidationMetric::new(&Split<Validation>, name, value)` accepted an arbitrary
f64.** Possessing a validation split does not prove the number came from it, let alone that it was
computed with the selected artifact. Replaced by an evaluator that takes both and computes.

**Review fix 2 — `mint_test_token(&self, candidate: [u8; 32])` trusted a caller-supplied hash.** A
caller could submit the locked hash and then evaluate an entirely different artifact. The parameter
becomes the verified run object.

**Review fix 3 — the lock omitted D-14's candidate history.** A single chosen metric cannot prove
validation-only selection: it is consistent with having tried ten configurations, peeked at test,
and reported the one that won there. The lock now commits every candidate and applies the rule.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| selection decision → canonical test access | THE domain access-control boundary (V4-analogous, D-14) |
| caller-supplied numbers → selection evidence | whether a metric is computed or merely claimed |
| a token in flight → the model it is used against | whether identity is re-checked at the point of access |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-27 | Repudiation | lock-then-tune-then-test passing | mitigate | token mintable only on artifact-hash match read from the run object; StaleLock names both hashes; the full sequence is a falsification test |
| T-3-28 | Tampering | rewritten lock record | mitigate | canonical bytes + SHA-256 binding, mutation test; append-only discipline (no removal API) |
| T-3-29 | Spoofing | metric from a compatibility/test split posing as canonical validation | mitigate | the evaluator requires `&Split<Validation>` by type; the compatibility profile cannot produce one (Ph2 D-19); the evaluation commits the validation-split fingerprint |
