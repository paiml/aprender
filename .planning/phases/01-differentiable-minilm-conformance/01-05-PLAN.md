  tests are in-module (`#[cfg(all(test, feature = "setfit"))]`), and 01-08's out-of-crate integration
  harness already drives through `SetFitMiniLm::from_slice_fixture` / `from_pretrained_dir`.

Checker-driven revision, iteration 2 (2026-08-08):
- **[W1 — the seal was bypassable at the DATA layer] `SentenceBatch`'s fields become `pub(crate)`
  with public READ accessors.** Every field was `pub`, including `tokenizer_sha256`. Sealing the
  constructors makes a mismatched *pair* unconstructible, but out-of-crate code could still
  hand-build a `SentenceBatch` literal stamped with a correct hash, or take a legitimate batch from
  `SetFitMiniLm::tokenize()` and mutate `input_ids` while leaving the hash intact — then feed either
  to `encoder().forward_tokens()`. D-08's letter survived that; the threat-register claim "the
  encoder rejects a mismatch at every forward call" did not, because the check compares a hash the
  attacker controls. Private-by-default fields close both holes with no cost to in-crate callers
  (01-06 is in the same crate) and no cost to 01-08 (it needs to READ `batch`/`seq` at most).
  `#[non_exhaustive]` is NOT added — it is redundant once the fields are `pub(crate)`, which already
  makes out-of-crate struct-literal construction and exhaustive destructuring impossible. (It is NOT
  rejected for restricting in-crate construction: `#[non_exhaustive]` is a no-op within the defining
  crate.)

  for every text any other fixture uses, so it has MORE cases than the six required classes. Task 2's
  parity test iterates ALL cases, so this strictly widens coverage; the `case count > 4` assertion
  still holds.

**Visibility rule for this whole module (D-08, user decision 2026-08-08):** every constructor that
