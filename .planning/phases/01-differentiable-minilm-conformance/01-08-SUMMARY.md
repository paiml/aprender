# Phase 1 Plan 08: Conformance Gate and Tier Wiring Summary

The phase gate exists, it is driven end to end from fixture **texts** through the
real tokenizer, every epsilon in it is generated from the versioned contract, and
each gate was turned **red** before it was trusted. The controlled AdamW step
matches the torch reference for all 37 tensors — decoupled weight decay included —
on the first run, and the full 6-layer / hidden-384 checkpoint was exercised once
so the phase is not being declared complete on slice evidence alone.

## What These Gates CAN and CANNOT Detect

Stated plainly, because 01-06's mutation F is the standard: an FFN output dropout
that was constructed, seeded, mode-aware and reported — but never called —
survived **41 of 42** tests there.

**Detected.** Wrong per-layer arithmetic, localized to the layer index (proven:
reversing the fixture's layer order fails with `case 'single_short' / layer 0`).
A tanh-form GELU (asserted in-band to fail the exact-erf gate). A wrong pooling
denominator (pooled and normalized are compared separately, so normalization
cannot mask it). A severed autograd edge anywhere the pair objective's backward
should reach. A wrong AdamW hyperparameter or a coupled decay. A frozen parameter
that moves, bitwise. A tokenizer disagreeing with the pinned HF one. A tolerance
loosened without a contract edit. A locally edited fixture.

**NOT detected — and this is the honest half.**

1. **Anything inert in EVAL mode.** Every numerical fixture was generated with
   dropout disabled (D-16), so a dropout site that is constructed and never
   applied is invisible to *every* parity gate in this file. That class is
   covered only by 01-06's
   `encoder_mode_every_site_is_actually_applied_in_the_forward`, which lives in
   the library's unit tests. This suite would have passed mutation F.
2. **Anything that needs the full architecture.** The slice is 2 layers /
   hidden 64 / 2 heads / 64 positions / 97 vocabulary ids. A hidden-384
   assumption, a 6-layer indexing bug or a 30522-vocabulary defect is reachable
   only through the `#[ignore]`d D-10 suite, which is not in any tier.
3. **Anything below the epsilon clamps.** Every fixture batch produces unit-norm
   rows, so the `n <= eps` branches of `l2_normalize_rows` and
   `cosine_similarity_rows` are never taken here. Their coverage is 01-03's unit
   tests, and this suite would not notice if that branch regressed.
4. **Ops composed with `include!()` are invisible to the mutation run.** See D51:
   `embedding_gather`, `masked_mean_pool`, `l2_normalize_rows`,
   `cosine_similarity_rows` and `mse_loss` generate ZERO mutants under a
   cargo-mutants file glob, so D-25's stated "autograd ops" scope was not
   actually mutated. What was mutated is recorded below.
5. **Train-mode numerics.** No fixture pins a training-mode forward, so seeded
   dropout reproducibility is asserted only by 01-06's unit tests.

## D-14: The Tolerances Live in One Place, and the Guard Was Turned Red

`tolerances_generated.rs` is emitted from
`contracts/setfit-encoder-conformance-v1.yaml` by
`schema::parse_contract` — **the same deserializer `pv validate` itself uses**, so
the generator cannot drift from pv's reading of the contract. The nine constants
reproduce 01-04's frozen table exactly.

**`pv` was checked first, as the plan required, and the finding is recorded either
way.** `pv codegen --help` offers only `[CONTRACT_DIR] -o <OUTPUT>`, and its
implementation walks preconditions / postconditions / invariants only —
`grep -c tolerance` over `commands/codegen.rs` and `commands/equations.rs` returns
**0** in both. `pv equations --format rust` exits 1 with
`error: unknown format 'rust', expected 'text', 'latex', 'ptx', or 'asm'`. So no
`pv` path emits tolerances today, exactly as the plan predicted, and path (ii) was
taken. Teaching `pv` to emit tolerances would be a real engineering task with its
own ticket; it was **not** silently attempted here.

**The in-tree parser had to be reached through an alias**, which is a finding in
itself (D53): `crates/aprender-core/[dev-dependencies]` already carries
`provable-contracts = "0.3"` — the **crates.io** package, while the workspace is
at 0.63.0 — and both packages declare `[lib] name = "provable_contracts"`. Writing
`use provable_contracts::` would have parsed the contract with a two-year-old
registry crate and reported a confident green about code not under change. That is
D10's class. The manifest records the reason at the dependency.

**The agreement test has been red, twice, deliberately:**

| Mutation | Result |
|---|---|
| `LOSS_PAIR` 7.6293945e-6 -> e-4 | `tolerance drift: LOSS_PAIR is 7.6293945e-4 … but 7.6293945e-6 in OBLIG-ENC-06-LOSS-FORWARD-PARITY` |
| one hex char in `CONTRACT_SHA256` | `the contract has changed since tolerances_generated.rs was generated` |

Both reverted. The single documented skip (contract not found, i.e. a packaged
crate) still requires `CONTRACT_SHA256` to be 64 lowercase hex characters.

**The generator emits rustfmt-stable output.** `CONTRACT_SHA256` is pre-wrapped
because the unwrapped line is 101 columns. That is D7 applied prospectively: a
generator whose output differs from the committed file makes every future drift
check 100% noise.

## D12: CLOSED

`contracts/setfit-encoder-conformance-v1.yaml` wrote the cosine denominator as
`max(‖a‖·‖b‖, eps)`; the implementation clamps each factor. The **prose** was
wrong, not the code — per-factor is what `torch.nn.functional.cosine_similarity`
does and what 01-03's four-branch finite-difference gradchecks presuppose. The
formula now reads the per-factor form, and the invariants record that the two
coincide wherever both norms exceed eps.

`pv validate contracts/setfit-encoder-conformance-v1.yaml` -> **rc=0, 0 errors,
0 warnings**. The implementation was not touched (`git diff` on
`autograd/ops/similarity.rs` is empty), and the reword provably moves no codegen
(table above).

## The Tokenizer Boundary (B6 / T-1-27)

Every model input in this harness comes from one helper:

```rust
pub fn batch_from_case(model: &SetFitMiniLm, texts: &[String])
    -> Result<SentenceBatch, SetFitError>
{
    let refs: Vec<&str> = texts.iter().map(String::as_str).collect();
    model.tokenize(&refs)   // the only public batch producer after the D-08 seal
}
```

- `grep -rn 'SentenceBatch *{' crates/aprender-core/tests/setfit_conformance/` -> **rc=1, no match**
- `grep -rn '\.tokenize(' <harness>` -> **exactly one line**, `setfit_conformance.rs:160`, inside `batch_from_case`
- `conformance_the_tokenizer_boundary_is_the_only_batch_source` re-checks both on every run, and additionally asserts the single call site is inside a function *named* `batch_from_case`

**The pre-remapped slice-id arrays are not deserialized at all.** The plan allowed
them "in diagnostic messages, if at all"; not reading them is strictly stronger,
because the harness then *cannot* feed ids the encoder should have remapped
itself. `conformance_the_harness_never_reads_a_pre_remapped_id_array` scans for
the field names in non-comment code.

**And the remap is proven reachable rather than assumed.**
`conformance_the_slice_batch_carries_canonical_ids_the_encoder_must_remap`
asserts the pair batch contains ids ≥ 97 (the slice vocabulary size); without it,
a no-op remap would satisfy every numeric gate in the file.

The `case_id` join is the triple equality the plan specified: for each fixture
case, `tokenizer_cases.json[case_id].input_ids` == the fixture's
`input_ids_canonical` == `batch.input_ids()` from the real tokenizer.

## ENC-04: One Gate, Two Models, and the D42 Trap

`assert_encoder_updates` implements `OBLIG-ENC-04-GRADIENT-AND-STEP-GATE`
verbatim — (a) finiteness with no exemptions, (b) non-zero *aggregate* per
contracted component, (c) per-tensor non-zero for non-exempt names, (d)/(e) the
exemption **two-sided**, (f) the same shape over post-step movement. All three
suites call the identical function, and
`detach_negative_uses_the_same_gate_helper_as_the_positive_suites` asserts that by
source scan.

`component_of` derives ENC-04's four components from `FreezeGroup::matches`
rather than a second prefix table — 01-07 already proves that partition covers all
37 names with no gaps, and a private copy could drift from the mapping the freeze
policy uses.

**D42 was honoured and then measured.** Every parameter set and every gradient
collection goes through `SetFitMiniLm::trainable_parameters_mut()`. Reproducing
01-07's mutation D here (the policy stays *reported* while the optimizer's
parameter set stops honouring it) fails with:

```
`encoder.layer.1.attention.self.query.weight` is frozen but its BITS moved
across the optimizer step
```

— the same tensor 01-07 named. **A structural note worth recording:** out of
crate, `trainable_parameters_mut()` is the *only* source of mutable named
parameters on `SetFitMiniLm` (`encoder()` returns an immutable borrow), so the
D42 mistake cannot actually be written in this harness. The mutation had to reach
for `clear_freeze()` to reproduce it.

### Model A / Model B are genuinely separate

`optimizer_step.json` records `all_trainable: true`. `gradient_gate.rs` asserts
`freeze_policy()` is empty and compares against the fixture; `frozen_gate.rs`
builds a *second* clean model, applies `FreezeGroup::LayerAttention(1)`, and
proves a purely internal property. `frozen_gate_never_compares_against_the_all_trainable_optimizer_fixture`
scans the file to keep it that way (T-1-24), and
`frozen_gate_frozen_tensors_are_bitwise_unchanged_across_an_adamw_step` asserts at
least one trainable tensor moved so it cannot pass vacuously.

### The controlled step matched on the first run

All 37 post-step tensors match `optimizer_step.json.post_step` within the frozen
`OPTIMIZER_STEP` tolerance, **including the weight-decayed parameters**. So
`rm_sprop.rs`'s decoupled decay (`param -= lr*wd*param` before the Adam update)
agrees with torch AdamW's `p.mul_(1 - lr*wd)`. **No tolerance was widened and no
divergence had to be documented.** Loss: `0.141698048 -> 0.138318941`, both
matched against the recorded values, and the strict decrease asserted.

Every hyperparameter is read from the fixture and configured explicitly
(`AdamW::new(params, lr).betas(b1, b2).eps(e).weight_decay(wd)`), never from
builder defaults — the fixture is the arbiter and defaults can drift.

## D-24: The Negative, and Why It Is Not Theater

The detached variant reads `.data()` off the pooled output, rebuilds with
`Tensor::from_vec`, and **explicitly** calls `requires_grad_(true)`. The test
asserts *both* halves: the rebuilt leaf receives a real gradient (so the loss is
differentiable and the severance is upstream) **and** the encoder parameters
receive none. Without the first assertion the test would pass for the wrong
reason — "nothing is differentiable anywhere".

Three mutations, applied, measured, reverted:

| # | Mutation | Result |
|---|---|---|
| 1 | optimizer parameter set stops honouring the freeze policy (D42) | frozen bitwise gate FAILS, naming `encoder.layer.1.attention.self.query.weight` |
| 2 | gate clause (a) stops reporting missing gradients | detached encoder is **still rejected**, by clause (b) — the component aggregates go to exactly zero. Two independent defences. The negative test still fails, because it also requires the report to NAME the parameters |
| 3 | gate returns `Ok(())` unconditionally | `the ENC-04 gate ACCEPTED a detached encoder…` |

Mutation 2 is the interesting one: it shows clauses (a) and (b) are not redundant
phrasings of one check.

`detach_negative_the_connected_encoder_passes_the_same_call` is the mirror —
without it, "rejects the detached variant" would also be satisfied by a gate that
rejects everything.

**D-24 scope, as accepted 2026-08-07:** this gate runs in every
`--features setfit,conformance-fixtures` pass and via `make tier2`. It is not in a
default-feature `cargo test`, because the entire harness is feature-gated. The CI
matrix legs are the approval-gated follow-up listed at the end of this document.

## D-26: Tier Wiring, Chosen From Measurement

### The placement rule, and why the pre-accepted fallback was NOT triggered

| command | wall | test time |
|---|---|---|
| whole conformance suite, one invocation | **7 s** | 0.57 s |
| one filtered invocation (`gradient_gate_`) | 6 s | 0.44 s |
| `--lib --features conformance-fixtures setfit::` | **19 s** | 1.72 s |
| `--lib --features setfit` (the plan's form) | 119 s | 64.11 s |

Wall clock is dominated by cargo's per-invocation freshness check, not by test
execution. The pre-accepted split (fast gates in tier2, `forward_parity` in
tier3) needs **three** invocations, because a `cargo test` line carries at most
one positional filter and `gradient_gate_` / `frozen_gate_` / `detach_negative_`
share no prefix — so it would cost ~18 s to avoid a 7 s run. **The fallback was
not triggered; the whole suite is in tier2 as one invocation.** The plan
estimated 10-30 s for the suite; it is 0.57 s.

The lib line uses the module path (D30). `--features setfit` runs 14202 tests of
which 162 are this phase's; `setfit::` selects exactly 162, and 162 is precisely
the feature-gated delta (14283 tests with `conformance-fixtures` vs 14121 with
default features), so the filter loses nothing.

`make contract-validate` was run **standalone first**, status captured directly:

```
rc=0        wall_seconds=8        41 contracts, each "0 error(s), 0 warning(s)"
```

Nothing is already red and 8 s is well inside tier3's 1-5 minute budget, so the
**broad** `@$(MAKE) contract-validate` form was used and the phase contract added
to `$(CONTRACTS)`. The narrow single-contract form was not needed, and no

stage goes through `pair_cosine_mse`, which uses the crate's own constant.
